# 适配器指南

> 已由 B 档 MetaWorld MT1 样例验证（开发机冒烟与自检 PASS，平台 oracle 全部成功）。B 档（有仿真、没有 vla-eval 适配器）在步 4～6 读本文。A 档不需要。
> 上游原则见 harness `skills/add-benchmark/SKILL.md`（tag v0.9.0），本文只写平台口径下要多注意的点。

## 1. 先追原评测，再写代码

步 4 填表单前，先把原评测代码的五段读完，每段记下 `文件:行`，写进 `form.yaml`（出处标签 `[源码]`）：

| 段 | 要找的东西 | 进适配器的哪里 |
|---|---|---|
| 任务选择 | 任务列表从哪来、顺序、子集（suite）怎么选 | `get_tasks()` |
| 初始化 | seed、初始状态（固定 init state 文件 / 随机采样）、warm-up 空步数 | `__init__` 参数、`reset()` |
| rollout | 每步动作怎么喂给仿真、动作维度与 gripper 处理、horizon | `step()`、`max_steps` |
| success | 成功判定的那一行（`info["success"]`、`done`、任务谓词） | `get_step_result()` |
| 收尾 | env 复用还是每 episode 重建、close 时机 | `reset()`、`cleanup()` |

G2 要求的四项（任务列表、seed、`max_steps`、success）就从这张表来。原评测有论文给出的 horizon 时，以代码为准，
论文与代码不一致写进交付说明。

## 2. 骨架

照 v0.9.0 的 `StepBenchmark` 写，LIBERO 适配器（`src/vla_eval/benchmarks/libero/benchmark.py`）是最好的参照：

```python
"""<name> 的 vla-eval 适配器。"""
from __future__ import annotations

from typing import Any

import numpy as np

from vla_eval import specs
from vla_eval.benchmarks import base

    render_backends = frozenset({"gpu"})        # 有 cpu 路径再加，见 渲染与资产.md

    @classmethod

        from vla_eval import render              # MuJoCo 系；SAPIEN 用 configure_sapien_render(mode, "<覆盖 ICD 的变量名>")
        return render.configure_mujoco_render(mode)

    def __init__(self, suite: str = "default", seed: int = 0, num_steps_wait: int = 0) -> None:
        super().__init__()
        self.suite, self.seed, self.num_steps_wait = suite, seed, num_steps_wait
        self._env = None

    def get_tasks(self) -> list[dict]:
        names = _load_task_names(self.suite)     # 未知 suite 直接 raise，不回落默认
        return [{"name": n, "suite": self.suite, "task_id": i} for i, n in enumerate(names)]

        return raw_obs

    def step(self, action: dict) -> base.StepResult:
        a = np.asarray(action.get("actions", action.get("action")), dtype=np.float32)
        assert a.shape == (7,), f"action dim {a.shape}"
        obs, reward, done, info = self._env.step(a)
        self._recorder.record_video(frame)
        return base.StepResult(obs=obs, reward=reward, done=done, info=info)

        return {"success": bool(step_result.info["success"])}   # 出处：<原评测 文件:行>

    def get_metadata(self) -> dict:
        return {"max_steps": 400, "suite": self.suite}

    def get_action_spec(self) -> dict:
        return {"position": specs.POSITION_DELTA, "rotation": specs.ROTATION_AA,
                "gripper": specs.GRIPPER_CLOSE_POS}

    def get_observation_spec(self) -> dict:
        return {"agentview": specs.IMAGE_RGB, "language": specs.LANGUAGE}

    def cleanup(self) -> None:
        if self._env is not None:
            self._env.close()
            self._env = None
```

`StepBenchmark` 把这些同步方法桥接到上游的 async 接口，不要自己实现 `start_episode` / `apply_action`。
仿真器一次调用推进多个 env 时，0.9.0 另有 `VectorStepBenchmark`（`num_envs`、批量 reset / step），要求 MS 声明 `vector_step` 能力，自定义 MS 多半不支持，平台口径下先按 `StepBenchmark` 写。

## 3. 逐项要求

| 项 | 要求 | 不满足时 |
|---|---|---|
| `get_action_spec` / `get_observation_spec` | 两个都必须覆写（默认 raise）；用 `vla_eval.specs` 里的常量表达维度、坐标系、增量 / 绝对、gripper 取值 | 第三条底线（动作语义）没有依据 |
| success | `get_step_result` 返回 **bool** `success`，取原评测的判定，不自己发明 | 自检 `result_has_success`（M7）FAIL |
| `get_metric_keys` | 默认 `{"success": "mean"}`；加自定义指标时保留 success | `metric_keys`（M7）FAIL |
| `max_steps` | `eval.yaml` 显式写正整数（平台据此算超时）；`get_metadata()["max_steps"]` 写同一个值作兜底 | `max_steps`（M11）FAIL |
| 未知 suite / task | `get_tasks()` 直接 raise | 0 episode，平台判 `bench_no_episodes` |
| 任务失败 vs 基础设施错误 | 任务没完成返回 `success=False`；仿真崩了、资产缺失让异常抛出去 | 把 infra 错误吞成 `False` 会产出看似正常的低分 |
| 录屏 | `reset` 后与每步各调一次 `self._recorder.record_video(frame)`，帧是 HWC uint8 RGB，方向摆正 | `video_count` / `video_decodable`（M9）FAIL |
| 观测图像方向 | 喂给模型的图与原评测逐像素同向，原评测不翻就不翻；只有录屏帧另行摆正（MetaWorld 的 `env.render()` 上下颠倒，原评测直接喂，适配器也直接喂，录屏转 180°） | 适配器擅自摆正，模型看到的图与训练分布不一致，分数静默变低 |
| 仿真器 import | 放进 `reset` / `_init_*` 里 | `--list`、配置解析阶段就要拉起仿真器，慢且易崩 |
| 实时模式 | 要跑 `mode=live` 时实现 `get_hold_action`：绝对控制用 `base.repeat_last_hold`，增量控制返回固定零动作 | live 评测 fail fast |
| env 复用 | 同 task 多 episode 可复用 env（LIBERO 做法），换 task 时 close 旧的 | 每 episode 重建可能慢到超时 |
| seed | 种子按 `episode_idx` 派生或取原评测的 init state 文件，两次冒烟结果可复现 | 分数不可复现 |
| `step_dt` | 每步仿真秒数（控制周期 × 每个动作推进的仿真步数），只在原评测源码能核实时写，否则留 `None` | 写错会让依赖仿真时钟的 MS 节奏错位 |
| `hard_exit` | 仿真器在解释器退出阶段崩溃（Isaac Kit 类）时设 `hard_exit: ClassVar[bool] = True`，结果落盘后 CLI 直接 `os._exit` | 退出码非 0，平台判失败 |
| 接管事件循环的仿真器 | Isaac Kit 类：懒启动、全部调用放进单线程执行器、覆写 `start_episode` / `apply_action` 去 `await` 它、线程栈调大，做法见 `上游缺口.md` 第 4 节 | 首次冒烟即坏，或只在集群小配额下段错误 |
| 按核数起线程的仿真器 | 线程数取 CPU 亲和性与 cgroup `cpu.max` 配额的较小者传给仿真器（Kit 是 `limit_cpu_threads`），不用 `os.cpu_count()` | 容器里拿到宿主机核数，集群小配额下被 CFS 节流，慢到首帧全黑或超时 |
| 首帧全黑兜底 | 只补渲染、不推进物理，上限按时长不按帧数，仍全黑就 raise | 推进物理会改 episode 口径；不 raise 会把渲染故障吞成低分 |
| `task_exclusive` | 原评测要求同一 task 的 episode 按初始状态顺序在一个进程里跑时设 `True`，shard 改为按整 task 认领 | 默认 `False`，episode 可跨 shard |
| `resume()` | 可选；排队续跑时收到已完成 episode 的结果，有跨 episode 状态（如布局队列）才需要覆写 | 不覆写即忽略 |

## 4. 放哪、怎么被找到

- 适配器写成一个普通 Python 包，放 `/opt/bench/<name>_bench/`（随镜像保存），在评测 env 里 `pip install -e /opt/bench/<name>_bench`
  或在 `start.sh` 里 `export PYTHONPATH=/opt/bench/<name>_bench:$PYTHONPATH`。二选一，写进 G3 计划。
- `eval.yaml` 的 `benchmark:` 写 `"<模块路径>:<类名>"`，例如 `"mybench.benchmark:MyBenchmark"`。
- 写完先在评测 env 里单独验：

```bash
"$BENCH_ENV/bin/python" -c "from vla_eval import registry; c=registry.resolve_import_string('mybench.benchmark:MyBenchmark'); \
b=c(); print(len(b.get_tasks()), b.get_metadata(), b.get_action_spec())"
```

## 5. 冒烟之前单独验一帧

harness 原则：先看真实相机输出，再跑冒烟。在评测 env 里 `reset` 一个 task，把首帧存成 png 拿回本机看：
不是全黑、物体在画面里、方向正确。冒烟只证明管道通，echo 动作下 success 应接近 0（M12 零动作对照）。
有 oracle 动作（原评测附带的示范轨迹、脚本策略）时一定回放一次，成功率须 > 0，否则 success 可能恒假或动作语义不一致。

## 6. 什么时候停

- 原评测的 success 判定在闭源服务或人工打分里，追不到代码：停下，告诉用户这条底线不满足。
- 原评测必须依赖网络（在线拉资产、调外部 API）：见 `渲染与资产.md` 第 3 节，平台运行时可能无外网。
- 需要改 harness 才能接（协议不够用）：见 `上游缺口.md`，只写 issue 草稿，不在开发机上 patch harness 源码树。
