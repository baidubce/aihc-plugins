# 冒烟测试

步 7 的门禁（G4）：`ba_selfcheck.py` 输出 `RESULT: PASS`（全部 shard 退出码 0 由其 `exit_code` 项判定）。任一不过回到步 6，
没有 `--skip`。冒烟用零动作 echo MS，**只证明管道通、不证明分数可信**；分数可信靠三条底线与 `--control` 对照。

## 1. 前置

| 项 | 检查 |
|---|---|
| vla-eval | 评测 env 里 `importlib.metadata.version('vla-eval')` 是 `0.9.0`；Python ≥ 3.11 |
| 图形栈 | `nvidia-smi` 正常；`ls /usr/share/vulkan/icd.d /etc/vulkan/icd.d` 有 `nvidia_icd.json` |
| 视频解码 | 跑自检的 Python 能 `import imageio.v3`（另需 `imageio-ffmpeg`） |
| 工作目录 | `$W` 在可写盘上，空间够放 N 个 shard 的视频 |
| Ray 环境 | 步 2 的 `ray_env_check.sh` 输出已存成 `$W/ray_env_check.log`，最后一行 `RAY_ENV_OK`（M3） |

## 2. 起 echo MS

用 `scripts/echo_ms.py`：直接复用 `vla-eval test` 的 echo server（`vla_eval.cli.smoke._make_echo_server`，每步回
`np.zeros(action_dim)`），用 `vla_eval.model_servers.serve.serve_async` 起服务，不依赖 docker。该工厂是上游私有符号，
harness 版本不是 v0.9.0 而找不到时脚本报错退出（退出码 3），不自行重写。用评测 env 的 python 跑：

```bash
nohup "$BENCH_ENV/bin/python" scripts/echo_ms.py --action-dim 7 --port-file "$W/echo.port" > "$W/echo.log" 2>&1 &
echo $! > "$W/echo.pid"
sleep 5; port=$(cat "$W/echo.port"); curl -s -o /dev/null -w '%{http_code}\n' "http://127.0.0.1:$port/config"   # 200 即就绪
```

`--action-dim` 与目标模型一致；冒烟结束 `kill $(cat "$W/echo.pid")`。

## 3. 跑冒烟

```bash
python scripts/smoke_run.py --workdir "$W/smoke" \
  --server-url ws://127.0.0.1:<port> --bench-name <name> \
  --command 'bash /opt/bench/start.sh' \
  --set EVAL_BA_NUM_SHARDS=2 [--set EVAL_BA_SUB_BENCH=<suite>] [--env KEY=V ...]
```

- `--command` 必须与交付给控制台的 command 逐字一致（G5）。含 `$`、`>`、`|` 等字符时脚本会告警：平台不经 shell 执行，
  这类 command 上平台后行为会变。command 自带 `--shard-id`、`--num-shards` 等平台下发的参数时同样告警。
- 每次冒烟用新的 `--workdir`（`$W/smoke-<序号>`）：目录里已有上次的产物时脚本直接退出（退出码 2），不删旧产物，
  以免新旧视频、日志、`.progress` 混在一起让自检误判。
- Ctrl-C 中断时脚本结束全部 shard 的进程组（先 SIGTERM，5 秒后 SIGKILL），返回 130；这次的产物作废，换新目录重跑。
- `--env` 填控制台条目里的 `envs`；`EVAL_BA_*` 只能用 `--set` 改。
- 默认 2 个 shard、每 task 1 个 episode、录屏开、`gpu` 渲染、`sync` 模式；验 0 卡路径再跑一次 `--set EVAL_BA_RENDER=cpu`
  （LIBERO 实测 cpu 渲染比 gpu 慢约 3.5 倍）。
- 实时模式另跑一次：`--workdir "$W/smoke-live" --set EVAL_BA_MODE=live`（保持 2 个 shard，`shared_queue` 要求 ≥ 2），
  再对这个目录跑自检。没实现 `get_hold_action` 或是 `VectorStepBenchmark` 时 harness 拒跑 live，`live_hold_action` 不过；
  后者只支持 sync，在交付说明里写明「不支持实时模式」。
- 开发机核数远多于平台配额时，按交付的 CPU 数再跑一遍：`CUDA_VISIBLE_DEVICES= taskset -c 0-<CPU-1> python scripts/smoke_run.py ...`（卡号置空，与平台单卡口径一致，见 `命令契约.md` 第 2 节）。
  `taskset` 只限亲和性，模拟不了集群的 CFS 配额（集群 Pod 看到宿主机全部核数、`cpu.max` 只给交付的几核）；开发机 cgroup 只读也没法改配额。
  所以按核数起线程的仿真器要在适配器里自己读 `cpu.max` 限线程数，不能只靠开发机冒烟证明。
  Isaac Sim 样例在开发机上一直正常，到集群小配额下才出现首帧全黑和段错误。
  这类仿真器重存镜像前，先按 `上游缺口.md` 第 5 节在集群上起单 Pod 复测。
- 冒烟前先在后台起 `scripts/shard_peak.py`，它按 session 认 shard，采每个 shard 的内存（PSS）、CPU，以及
  `/dev/shm`、显存、容器 cgroup 内存工作集相对冒烟前的增量，shard 全部退出后自动结束，并按交付口径换算建议资源：

```bash
nohup python scripts/shard_peak.py --out "$W/smoke/peak.json" --plan-shards <N> --plan-gpus <G> \
  > "$W/smoke/peak.log" 2>&1 &
```

  同机有别的 GPU 任务时显存增量会偏大，交付前看一眼 `peak.json` 的 `gpu_peak_delta_mib`。
  `suggest` 的 CPU = 2N，shm = N × 单 shard 峰值，每卡显存 = N / G × 单 shard 峰值。
  内存按 Pod 计，因为平台按 Pod 的 cgroup 限内存：单 shard 取「PSS + shm」与「cgroup 工作集增量 / shard 数」的较大者，
  内存 = (N × 单 shard + 2 GiB Ray 常驻 + N × 0.5 GiB Actor) × 1.5。冒烟不经 Ray，后两项是经验值；
  冒烟只跑少量 episode，长跑会涨，所以留 1.5 倍余量。
  `peak.log` 里的 `NOTE:` 行（单 shard CPU 峰值超 2 核、shm 低于控制面显式值下限、N 不能整除卡数、
  读不到 cgroup）原样写进交付说明。

产物：`$W/smoke/out/recording-em-smoke.sqlite`、`$W/smoke/videos/shard<i>/`、`$W/smoke/logs/shard<i>.log`、
`$W/smoke/smoke_env.json`、`$W/smoke/graphics_env.json`（子进程实际拿到的图形栈变量，查渲染设备时看它）、
`$W/smoke/progress_seen.json`（各 shard 运行期间读到的 `.progress`）、`$W/smoke/smoke_run.json`（实际执行的 command
与各 shard 退出码，供 M2、M4 与 G5 核对）。harness 在 benchmark 结束时删掉 `.progress`，
所以 `smoke_run.py` 在 shard 运行期间每 0.5s 轮询一次并记录。shard 非 0 退出先看对应 log。

## 4. 跑自检

```bash
python scripts/ba_selfcheck.py --db "$W/smoke/out/recording-em-smoke.sqlite" \
  --env-file "$W/smoke/smoke_env.json" --ray-env-log "$W/ray_env_check.log" --control --out "$W/selfcheck.json"
python scripts/ba_selfcheck.py --list    # 列出全部检查项与排查提示
```

`--progress-file`、`--smoke-file`、`--ray-env-log` 缺省取 `--env-file` 同目录的 `progress_seen.json`、`smoke_run.json`、
`ray_env_check.log`，`live_hold_action` 读同目录的 `logs/shard*.log`。退出码：0 全过，1 有 FAIL，2 自检本身跑不起来（DB 不在、env 缺键、没装 imageio）。

| 检查项 | M | 判定 |
|---|---|---|
| `command_literal` | M2 | command 不带平台经 `EVAL_BA_*` 下发的参数；`start.sh` 里 `--shard-id`、`--num-shards`、`--server-url`、`--eval-id`、`--output-dir`、`--render`、`--param suite=` 及 `name` / `episodes_per_task` / `mode` / `recording.output_dir` 字段都引用 `EVAL_BA_*`，不写字面量；这四个字段一个不能少；`--config` 指的 `eval.yaml` 里 `server.timeout` 写 `${oc.env:EVAL_BA_SERVER_TIMEOUT}`，不带默认值 |
| `ray_version` | M3 | 只查版本：`ray_env_check.log` 无 `[FAIL]` 且最后一行 `RAY_ENV_OK` |
| `exit_code` | M4 | 全部 shard 退出码 0 |
| `live_hold_action` | M5 | shard 日志里没有 harness 拒跑实时模式的报错（`does not implement get_hold_action`、`runs in sync mode only`）；只在 live 冒烟里会触发 |
| `db` | M4 | `$EVAL_BA_OUTPUT_DIR/recording-<eval_id>.sqlite` 存在且可读 |
| `progress` | M5 | 每个 shard 运行期间都读到过 `.progress`，且 `total` > 0（平台靠它报进度） |
| `param_match[.<子项>]` | M5、M6 | 每个 shard 的运行后核对与平台同口径：单条目、shard、录屏块、render、mode、server_timeout、episodes_per_task、env（M5）、harness_version（M6） |
| `result_has_success` | M7 | 每个 episode 带 bool `success`，且无 episode 报错 |
| `metric_keys` | M7 | `get_metric_keys()` 含 `{"success": "mean"}` |
| `shared_queue` | M8 | ≥ 2 个 shard 共用 `work_queue`，episode 不重不漏、全部 done |
| `video_count` | M9 | 每个 shard 视频数 = episode 数；0 个 episode 不过 |
| `video_decodable` | M9 | 可解码、非 0 帧、帧数与 `steps` 相差 ≤ max(2, 5%) |
| `render_device` | M10 | gpu 渲染时 env 不含 lavapipe / llvmpipe 等软渲染 ICD，画面非全黑；录屏开却没有可解码视频不过 |
| `max_steps` | M11 | `eval.yaml` 显式写正整数 `max_steps`，episode 步数不超过它 |

`--out` 的 JSON 里 `harness_config` 是冒烟实际生效的配置（已脱敏），原样写进交付说明。

## 5. `--control` 对照（M12）

只能证伪、不能证明。冒烟本身就是 echo MS 的零动作跑法，`--control` 直接把 `--db` 当零动作对照；
另跑过零动作对照时用 `--control-db` 指过去：

```bash
python scripts/ba_selfcheck.py --db ... --env-file ... --control [--oracle-db <oracle 回放的 DB>]
```

- 零动作：成功率须 ≤ 10%，否则 success 判定可能恒真；
- oracle：用户提供 oracle 动作时回放，成功率须 > 0，否则 success 判定可能恒假或动作语义不一致；没有 oracle 写「未验证」。

## 6. 失败排查

| 现象 | 常见原因 | 处理 |
|---|---|---|
| shard 非 0 退出，log 里 `Address already in use` | 固定端口 | 改绑 0 或按 `EVAL_BA_SHARD_ID` 错开 |
| `command_literal` FAIL | command 或 `start.sh` 写死了 shard、地址、输出目录、suite 等 | 照 `命令契约.md` 模板改成引用 `EVAL_BA_*` |
| `command_literal` 报「缺 --benchmark-field」或 `server.timeout` | 漏传 `mode` 等平台字段，或 yaml 写死了 timeout；冒烟默认值与 harness 默认值相同，运行后核对查不出来 | 照 `命令契约.md` 模板补齐 `--benchmark-field` 与 `timeout: ${oc.env:EVAL_BA_SERVER_TIMEOUT}` |
| `smoke_run.py` 退出码 2 | `--workdir` 里有上次的产物 | 换新目录 `$W/smoke-<序号>` 重跑 |
| `live_hold_action` FAIL | 适配器没实现 `get_hold_action`，或是 `VectorStepBenchmark` | 按 `适配器指南.md`「实时模式」补；`VectorStepBenchmark` 在交付说明里写明只支持 sync |
| `ray_version` FAIL | 没存 `ray_env_check.log`，或镜像 PATH 上的 ray 不对 | 重跑 `ray_env_check.sh` 存日志；非 base 镜像见 `Ray环境.md` |
| `db` FAIL | `start.sh` 改写了 `--output-dir` / `--eval-id` | 照模板直接传 `EVAL_BA_*` |
| `progress` FAIL | 改写了 `--output-dir`、`name` 没用 `$EVAL_BA_BENCH_NAME`，或没传 `--shard-id` / `--num-shards` | 照模板写 `eval.yaml` 与 `start.sh`；`progress_seen.json` 须是本次冒烟写出的 |
| `param_match.mode` / `.record_step` | yaml 写死了 mode 或 recording | 删掉 yaml 里的这些键，由 `--benchmark-field` 施加 |
| `param_match.server_timeout` | yaml 没引用 `${oc.env:EVAL_BA_SERVER_TIMEOUT}` | 改 `server.timeout` |
| `param_match.single_entry` | yaml 有多个条目 | 只留一个 |
| `result_has_success` | success 是 int / 缺失，或 episode 抛异常 | 改 `get_step_result`；看 `failure_detail` |
| `shared_queue` 报 `duplicated` | `start.sh` 自己循环 shard | 删掉循环，单 shard 执行 |
| `video_count` 少 | 没调 `self._recorder.record_video(frame)` | 每步录一帧 |
| `video_decodable` 坏 mp4 | 进程被 kill、recorder 未收尾 | 确认 `exec` 且正常退出；atexit 崩溃时适配器设 `hard_exit = True`（见 `上游缺口.md` U8） |
| `render_device` 软渲染 | 镜像 `ENV` 写死了 `VK_ICD_FILENAMES` / `MUJOCO_GL=osmesa` | 渲染变量只在构建期单条 `RUN` 里设 |
| `render_device` 全黑 | 相机、光照或 EGL 设备号不对；Kit 系冷启动时还没出图 | 先单独渲染一帧核对；Kit 系见 `上游缺口.md` 第 4 节，只补渲染、不推进物理 |
| shard 段错误（-11），开发机不复现 | CPU 配额小、`CUDA_VISIBLE_DEVICES` 与开发机不同；Kit 系还可能是线程栈不够 | 按上文第 3 节限核复测；Kit 系见 `上游缺口.md` 第 4 节 |
| `max_steps` FAIL | yaml 没写或写成 bool | 写正整数，取原评测的 horizon |
