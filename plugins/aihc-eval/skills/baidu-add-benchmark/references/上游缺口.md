# 上游缺口

> 第 4、5 节（C? 档、集群单 Pod 复测）已由 Isaac Sim 5.1 样例验证，其余部分未验证。接入时发现 harness（vla-eval v0.9.0）能力不够、或步 3 分到 C? 档时读本文。
> 本文只覆盖接入时会碰到的部分。

## 1. 纪律

- **不在开发机上 patch harness 源码树**，也不 `pip install` 自己改过的 harness。镜像里的 harness 版本必须与平台 Head 一致
  （recording DB 与 `.progress` 格式未成文，见 U5），改过的 harness 产出的 DB 可能合并失败或静默错位。
- 能在适配器、`start.sh` 里绕过去的，用下表的过渡做法绕过去，交付说明写明绕了什么。
- 绕不过去的：停下，写 issue 草稿给用户。草稿是英文标题 + 中文要点（现象、复现、期望行为、平台过渡做法），
  **用户确认后由用户自行改写成英文提交**，skill 不对外提交任何 issue / PR。先 issue，维护者确认方向后才提 PR。
- 草稿里不得出现凭据、开发机地址与端口，也不要贴需要登录才能访问的页面链接。

## 2. 已知缺口与过渡做法

| # | 缺口 | 接入时的表现 | 过渡做法 |
|---|---|---|---|
| U1 | runner 不校验 `get_result()` 的键与类型 | `success` 缺失或是 int 时 episode 照样计入 | 适配器返回 bool `success`；自检 `result_has_success`（M7）与数据面 `shard_invalid_result` 兜底 |
| U2 | 开录屏但 0 帧不报警 | 视频为空、无提示 | 每步调 `record_video`；自检 `video_count` / `video_decodable`（M9） |
| U3 | export 不按 suite 聚合 | 多 suite 时分数混在一起 | 平台按 `(suite, task_idx)` 重组（`bench_result.py`）；**适配器的 task dict 要带标量 `suite` 字段**，否则全部归到默认组 |
| U4 | `get_metadata()` 无标准 `version` 键 | 结果无法追溯评测集版本 | 交付说明写评测集版本与原评测代码 commit |
| U5 | recording SQLite / `.progress` 格式未成文 | 换 harness 版本可能静默不兼容 | 镜像用 v0.9.0，与平台镜像同版本；不自行升级 |
| U6 | 没有远程 benchmark 转发协议 | 仿真跑在独立服务里时接不进来 | 自写 `Benchmark` 子类在 `start_episode` / `apply_action` 里转发（未实测） |
| U7 | CLI 不读 `VLA_EVAL_*` 环境变量 | 平台经 `EVAL_BA_*` 下发参数 | `start.sh` 手写 env → 参数映射（`命令契约.md` 模板） |
| U8 | 解释器退出阶段崩溃（0.9.0 已补） | Isaac Sim Kit 插件 atexit 段错误，进程非 0 退出，平台判失败 | 适配器设 `hard_exit = True`，见第 4 节 |
| U9 | 没有 `vla-eval test --benchmark --no-docker` | 改完适配器缺快速自测入口 | 用本 skill 的 `smoke_run.py` + `echo_ms.py` |
| U10 | watchdog `os._exit` 前不打调用栈 | 卡死只留超时信息 | 适配器里可自行 `faulthandler.register(signal.SIGUSR1, all_threads=True)` 便于手工取栈（未实测） |

另一处差异：`auth_token` / `VLA_EVAL_SERVER_TOKEN` 只在平台镜像 `/root/workspace/vla-evaluation-harness` 的 harness
里有，上游 v0.9.0 没有。步 2 探测要求 `auth_token=有`，所以评测 env 的 harness 应来自镜像里那份，
不要从 PyPI / GitHub 另装上游版本覆盖。

## 3. 平台侧还没有的能力

| 项 | 影响 | 接入时怎么办 |
|---|---|---|
| per-group 镜像凭据 | MS 与 BA 镜像分属不同私有仓库时可能拉不下来 | 建议用户把 BA 镜像推到公开仓库或与 MS 同一凭据 |
| 单卡自定义 BA 不下发 `gpus_per_instance` | `CUDA_VISIBLE_DEVICES` 为空，Kit 等依赖 CUDA 的仿真器看不到设备；控制台 envs 也不让填 `CUDA_VISIBLE_DEVICES` | `start.sh` 里 `export CUDA_VISIBLE_DEVICES="${CUDA_VISIBLE_DEVICES:-0}"`（`命令契约.md` 第 2 节），镜像直接在控制台提交即可；冒烟用 `CUDA_VISIBLE_DEVICES=` 置空复现。不要靠绕过控制台创建的临时任务补 `benchmark_env`：用户自己提交时没有这一步，交付等于没过 |
| 卡死现场采集 | shard 卡死时只有日志与 `.progress`，没有调用栈 | 冒烟时留意单 episode 耗时；卡在原生调用里的问题在开发机上用 `py-spy dump` 先查清 |
| 环境的控制面没升级时，Head 镜像带的 harness 仍是旧版 | Head 按自身版本下发 `EVAL_BA_HARNESS_VERSION`，与 BA 的 0.9.0 对不上，episode 全部跑完后 shard 仍判 `shard_param_mismatch`，结果 `ALL FAILED` | 镜像绕不过。提交前看该环境下发的 Head 镜像 tag（`aihc-eval_head:h090-*` 才是 0.9.0）；不是就请联系平台升级控制面，不要靠绕过控制台创建的临时任务换 Head 镜像来交付 |

## 4. C? 档（Isaac Sim / Omniverse 系）

步 3 读到 `grade_hint=C?` 时先停下，把下面几条讲给用户，用户确认继续才往下走：

| 风险 | 说明 | 做法 |
|---|---|---|
| 无 cpu 渲染 | Isaac 在无 GPU 时报 `ERROR_INCOMPATIBLE_DRIVER` 或启动期 core dump | `render_backends = frozenset({"gpu"})`；交付说明写明不支持 0 卡 |
| atexit 段错误（U8） | 评测已跑完、结果已落盘，退出时段错误，退出码非 0 | 适配器类上设 `hard_exit: ClassVar[bool] = True`，见下方；**不要在适配器 `cleanup()` 里 `os._exit`**：v0.9.0 先调 `cleanup()`（`orchestrator.py:542`）后关 recording DB（`:238`），提前退出会丢结果 |
| 多卡铺到 0 号卡 | Kit 默认用全部可见卡渲染 | 把平台下发的 `EVAL_EXTRA_KIT_ARGS` 原样拼进 Kit 启动参数（`渲染与资产.md` 第 3 节） |
| 冷启动长 | shader 编译、资产加载可能几十分钟 | 平台启动阈值 `EVAL_SHARD_STARTUP_TIMEOUT_S` 默认 3600s、进度停滞阈值 `EVAL_SHARD_STALL_TIMEOUT_S` 默认 10800s；冒烟时记下首个 episode 前的耗时写进交付说明，超过 3600s 的告诉用户。集群节点驱动与开发机不同时，镜像里的着色器缓存用不上，开发机测的冷启动偏乐观，以集群单 Pod 复测（第 5 节）为准；Isaac Sim 样例在 4 核配额下首个 episode 约 6 分钟，开发机不到半分钟 |
| 资产与缓存大 | 资产几十 GiB；Kit 缓存要可写 | 资产进根盘，缓存按 `EVAL_BA_SHARD_ID` 分目录（`渲染与资产.md` 第 5 节） |
| 显存 | 每个 shard 一份 Kit，显存占用大 | 以 `shard_peak.py` 的 `gpu_peak_mib` 为准，必要时减 shard 数或加卡 |
| Kit 接管事件循环 | `SimulationApp` 的 async_engine 会接管所在线程的事件循环，放在 orchestrator 的循环上，首次冒烟就会坏 | 首次 `reset` 时懒启动 `SimulationApp`；Kit 的全部调用放进单线程 `ThreadPoolExecutor`，`start_episode` / `apply_action` 改成 `await asyncio.wrap_future(...)`；起 Kit 时临时把 `signal.signal` 换成空函数（非主线程注册会抛错），`sys.argv` 截到 `[:1]`（Kit 会解析它） |
| 集群上段错误（-11） | 核数多的开发机不复现；集群小配额下，app ready 后建相机节点（replicator `OgnReadFabricTime`）时 usdGeom 递归 256 层后崩溃 | 建 Kit 线程时临时 `threading.stack_size(64 MiB)`，建完恢复原值。线程在第一次 `submit` 时才创建，要在调大栈的期间先 `submit` 一次 |
| Kit 线程数按宿主机核数 | `SimulationApp` 取 `min(os.cpu_count(), limit_cpu_threads)`（默认上限 32）定 carb.tasking / TBB / `PXR_WORK_THREAD_LIMIT` 线程数；容器里 `os.cpu_count()` 是宿主机核数（集群节点常有上百核），而 BA Pod 的 CFS 配额只有几核，32 个线程被节流，60 步要 3 分钟，着色器编译拖到首帧全黑 | 起 Kit 时传 `limit_cpu_threads` = min(CPU 亲和性, ceil(`cpu.max` 配额 / 周期))，读不到 cgroup 时退回亲和性 |
| 首帧全黑 | 冷启动或 CPU 配额小时，`reset` 里的几步渲染可能还没出图 | 只补渲染（`world.render()`）、不推进物理，期间每帧重取图像；**上限按时长（如 300s）不按帧数**：配额小时 `render()` 返回很快但着色器编译跟不上，60 帧在集群上 15s 内就用完。仍全黑才报错，episode 口径不变 |
| Kit 缓存与日志写进 env | Isaac pip 包以 `--portable` 起，缓存、数据、日志写到 `site-packages/isaacsim/kit/{cache,data,logs}/`，开发机冒烟产物会随镜像保存 | 收尾清理时删掉这三个目录，删后再冒烟一次确认无缓存冷启动正常 |

`hard_exit`（v0.9.0 `benchmarks/base.py:69`）：orchestrator 实例化 benchmark 后记下它（`orchestrator.py:326`），
CLI 在结果写完后经 `os._exit` 退出，跳过解释器终结；真失败的非 0 码照样传出（`cli/main.py:221-251`）。
`start.sh` 末行仍是原样的 `exec vla-eval run ...`，不再需要 v0.8.0 时的 `run_exit.py` 包装入口。

C? 档目前只有一个 Isaac Sim 5.1 样例经集群单 Pod 复测与平台普通创建接口正式评测验证。其他 C? 档评测集未经验证，
交付说明须注明「C? 档未验证流程」，等平台正式评测通过后才能去掉。
**交付前要能在控制台直接提交成功**：靠派生 RayJob、手改 `EVAL_SPEC` 才通过的不算交付，平台缺口能在 `start.sh` 里绕的必须绕进镜像。

## 5. 集群单 Pod 复测

开发机和 BA Pod 有三处差异，开发机冒烟证明不了集群行为：

| 差异 | 开发机 | BA Pod |
|---|---|---|
| CPU | 宿主机全部核数，cgroup 只读，`taskset` 只限亲和性 | 亲和性仍是宿主机全部核数，`cpu.max` 只给交付的核数 |
| 驱动 | 开发机所在节点的驱动 | 集群节点驱动可能不同，镜像里的着色器缓存用不上 |
| `HOME` | 冒烟可自选 | 平台口径 `/root`，各 shard 共用 |

**什么时候做**：C? 档、或仿真器按核数起线程的，开发机冒烟过了之后、交付之前做一次；正式评测失败、开发机又不复现时，
**先做这个，不要改一版就重存镜像提交一次**。起 Pod 是集群写操作，先征得用户同意。

**Pod 怎么起**（与 BA 同口径；需要集群访问权限，没有权限时跳过本节，按交付说明与普通创建接口复现）：

- 镜像：用户最近一次保存的镜像（私有仓库凭据沿用该评测任务的 imagePullSecret，删任务前先删 Pod）；
- 调度：与 BA 同一资源池的 toleration 与 nodeAffinity；volcano 集群先 `kubectl create` 同名 PodGroup（`minMember: 1`、同一 queue），
  Pod 带 `scheduling.k8s.io/group-name` 注解、`schedulerName: volcano`；
- 资源：`limits` = `requests`，CPU、内存取交付说明的建议值，1 卡；`/dev/shm` 挂 Memory emptyDir（10Gi）；
- env：`HOME=/root`、`CUDA_VISIBLE_DEVICES=`（置空，与平台单卡口径一致）、`NVIDIA_DRIVER_CAPABILITIES=all`；`command: [sleep, infinity]`，`restartPolicy: Never`；
- 进 Pod 先看 `nproc`、`cat /sys/fs/cgroup/cpu.max`、`nvidia-smi` 驱动版本，确认确实是配额而不是整机。

**跑什么**：镜像里的适配器先备份，改过的适配器与 `scripts/` 冒烟脚本 `kubectl cp` 进去；去掉 `run_all` 里给开发机用的
`taskset` / `CUDA_VISIBLE_DEVICES`，原样跑 echo 冒烟 → `ba_selfcheck.py --control` → oracle 冒烟，同时起 `shard_peak.py`。
一个脚本串起来、`setsid nohup ... </dev/null &>/dev/null &` 后台跑，写完成标记，轮询标记而不是挂着 `kubectl exec`。

**过的标准**：echo 自检 `RESULT: PASS`、零动作 ≤ 10%、oracle 与开发机一致（成功数相同，每个 episode 的步数逐条相同），
`shard_peak.py` 的 `suggest` 不超过交付值。首个 episode 耗时记进交付说明。

**看起来卡住时**，先取证再下结论：

| 看什么 | 命令 | 判读 |
|---|---|---|
| 节流 | `cat /sys/fs/cgroup/cpu.stat` | `nr_throttled / nr_periods` 接近 1 说明配额吃满 |
| 线程 | `top -H -p <pid>`、`ls /proc/<pid>/task \| wc -l` | 哪些线程在转，是否远多于配额 |
| Kit 实际线程数 | Kit 日志里的 `threadCount` | 应等于 `_cpu_budget()` |
| 卡在哪 | `py-spy dump --pid <pid>`（加 `--native` 看原生栈） | 栈在推进还是始终同一处 |

隔 1～2 分钟取两次栈：位置变了就是慢，不是死锁。Isaac Sim 在小配额下常停在 `World.reset` 的 PhysX 初始化里
（`initialize_physics`，原生栈在 `carb.tasking` 等待），看着像死锁，几分钟后自己走完；取证前就改线程数会白改一轮。

**收尾**：通过后把同一份适配器落回开发机并核对 md5，Pod 里的 `$W` 打包归档到本地（`PROGRESS` 追加一行复测结论），
删掉 Pod 与 PodGroup，再让用户重存镜像、提交正式评测。复测 Pod 不进镜像，里面的缓存不用清。

**几条教训**：

- 「开发机能过、集群不过」时，每改一版就重存镜像、提交一次正式评测，往往要来回好几轮；先在集群单 Pod 上复现、取证、验证，通常一轮就能确认修法。
- 复测 Pod 的 env 要与平台下发的一致：手动设 `CUDA_VISIBLE_DEVICES=0` 会掩盖平台不下发卡号的问题（第 3 节），应置空。
- 绕过控制台创建的临时任务只用来定位问题。它常常顺带换了 Head 镜像或补了 env，会把平台缺口一起盖住；交付验证必须走普通创建接口。
