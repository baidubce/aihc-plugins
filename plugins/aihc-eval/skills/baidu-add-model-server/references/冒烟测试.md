# 冒烟测试（L1 协议级）

本 skill 的交付门禁只有一级：

| 级别 | 在哪跑 | 验什么 | 门禁 |
|---|---|---|---|
| **L1 协议级** | 开发机本机，阶段 5 | 服务自己满足协议、能真推理 | `ms_selfcheck.py` n/n 通过 + 退出码 0，**不过不交付** |

交付后用户在控制台以用户自定义镜像提交的平台级冒烟**不在本 skill 范围**，但 L1 必须先过：
平台侧一次排队 + 节点发现（可耗 600s）+ MS 启动（可耗 900s）才看到第一行进度，
而 L1 的三类真机缺陷（端口展开、必填字段、WS 握手被顶）在本机 30s 内就能暴露。

---

## L1：协议级冒烟

### 前置检查

阶段 5 起，两个脚本与 `obs.<benchmark>.json` 都已被 `setup.sh` 落到 **`/opt/ms-<name>/`**，自检入口只认这里
（原因见 `SKILL.md`「阶段 5」）。`$MODEL_ENV` 取 `setup.sh` 里的同一个值
（见 `开发机改造.md`「体检」判出的模型环境），自检脚本的依赖就装在它里面。

| 要求 | 检查命令 | 说明 |
|---|---|---|
| Ray 解释器约束 | `bash /opt/ms-<name>/ray_env_check.sh` | 要 `RAY_ENV_OK` + 退出码 0 |
| 自检脚本依赖 | `"$MODEL_ENV/bin/python" -c "import websockets, msgpack, numpy"` | **必需**；缺一个就跑不起来 |
| 图像编码依赖 | `"$MODEL_ENV/bin/python" -c "import PIL"` | 可选：缺 pillow 时 png/jpeg 两条**记 INFO 跳过**，不计 FAIL |
| 权重已就位 | `ls -d <ckpt 路径>` | 用**开发机上的真实路径**，`per_benchmark` 时每个 benchmark 各验一条；步 8 控制台填平台挂载后的路径（见下「ckpt 路径口径」） |
| GPU 可见 | `nvidia-smi -L` | 一卡即可；MS 运行形态是 `num_gpus=1` |
| 端口空闲 | `ss -ltnp \| grep :18000` | 自检固定用 18000，被占先换号 |

**ckpt 路径口径**：自检一律以**开发机上的真实路径**为准。步 8 交付的启动命令里，`--ckpt` 的值改成
**平台挂载后的路径**，这是整条命令里**唯一允许与自检不同的字段**，其余（含 `--config <benchmark>.yaml`）逐字等于
该 benchmark 那一遍自检。
平台路径由提交评测时的 `ckptPath` 决定、改造阶段还不存在，**不要反过来去对齐一个未知量**，也不要用软链硬凑同一字面。
它可以不同的前提是**ckpt 参数无默认值**：填错即启动失败并在日志里打出实际路径，不会静默跑出一份错分数——
所以「日志里 ckpt 路径对不对」这条人工项要核的是**平台路径**，不是与自检路径的字面一致。

### 两个终端

终端 A 起 MS，**必须用运行时同口径**（`env -i` 只带镜像 ENV + 代理指死端口 `127.0.0.1:9`），
命令见 `开发机改造.md`「自检」。

**就绪判据只有一个：`GET /config` 返 200**——平台也只探这个，2s 一次，900s 上限：

```bash
curl -s -o /dev/null -w '%{http_code}\n' -m 5 localhost:18000/config          # 要 200
curl -s -m 5 'localhost:18000/config?max_batch_size=1'                        # 带 query 也要 200
```

服务端日志里的 `[ms] listening on 0.0.0.0:18000` 只是**参考信号**，不作为判据：它由你自己的代码打印，
打早了（监听前就打）或打晚了都可能，而 `/config` 200 是平台实际用的那条。

⚠️ 反过来，`/config` 返 200 也**只证明端口通了，不证明能推理**。权重加载与 warmup 必须在监听之前完成——
先监听后加载会让平台以为已就绪，第一帧直接撞 act timeout。

### 终端 B 跑自检

```bash
"$MODEL_ENV/bin/python" /opt/ms-<name>/ms_selfcheck.py \
  --url ws://127.0.0.1:18000 \
  --obs-spec /opt/ms-<name>/obs.<benchmark>.json \
  --steps 3 --first-frame-budget 30
```

多选了 N 个 benchmark 就**每个 benchmark 各一遍**：终端 A 以 `--config /opt/ms-<name>/<benchmark>.yaml` 重起 MS，
终端 B 换成同名的 `obs.<benchmark>.json`。yaml 与 obs 必须同名配对——拿 A 的 obs 测 B 的 yaml 会以 A 的口径自洽通过。

**不要用裸 `python3`**：重档机（NGC / 裸 PyTorch）的 `python3` 往往是系统解释器，没装 `websockets`/`msgpack`，
会以 ImportError 挂掉，看起来像脚本坏了、实际是解释器选错。

`--list` 看用例名。判读**只按用例总数核，不按打印的 `n/n` 核**：`--skip` 会同时缩小分子分母，
跳掉用例后照样打印「n/n 通过」，所以交付门禁的绝对口径是**通过数 == 用例总数、退出码 0、且全程未带 `--skip`**。
**任何一条 FAIL 都不许交付**——逐条含义见 `协议自检.md`。唯一的合法跳过是缺 `pillow` 时 png/jpeg 两条
**由脚本自动降 INFO**（不是人工 `--skip`）；它仍意味着该编码没被验证，线上若会用到就补 `pillow` 重跑。
`--skip` 仅供改造中途快速试跑，交付门禁一律不带——`session_isolation`/`seq_echo`/畸形帧容错这类都是
真机缺陷用例、不是「不适用」项，不许用 `--skip` 跳过（闭源栈无法机械验时按 `接入表单.md` 末节人工论证，仍不跳）。

脚本看不到服务端日志，这三条只能人工看终端 A：

- [ ] `loading checkpoint: <路径>` 打的就是你传入的那个 ckpt
- [ ] `warmup ok, actions shape=(...)` 的维度与 `get_action_spec` 一致
- [ ] 没有「监听已开始但仍在 loading」的交错日志

### 清理后必须复跑一次

阶段 6 的清理（删 pip cache / HF cache / 代理行 / history）有误删风险，**清理后按同一条命令复跑 L1**，
仍要「通过数 == 用例总数」+ 退出码 0 才算交付（同样不带 `--skip`）。

## Troubleshooting

症状 → 先查哪里。**左列是你能看到的表象，右列是真正的根因位置**——这两者在本平台经常离得很远。

| 症状 | 先查什么 |
|---|---|
| `server rejected WebSocket connection: HTTP 200`，但 `curl /config` 全程正常 | `process_request` **按路径分流**了。BA 连的是无路径 `ws://<pod_ip>:<port>`（`request.path == "/"`），把 `/` 也当 `/config` 应答会顶掉握手。改成先判 `Upgrade: websocket` 头再分流 |
| MS 起不来，报错指向 `--port`，端口值像 `18000}` | `serve.sh` 写了 `${MS_PORT:?msg}` 且 msg 里含 `}`，提前闭合了参数展开。改成 `PORT="${MS_PORT:-}"` + 「纯数字第一参数」条件覆盖 + 显式 `[ -n ]` 校验 |
| 日志只说 `ModelServer exited prematurely (rc=2)`，细看是 `argument --port: expected one argument` | 控制台命令里没写 `{port}`，而 `serve.sh` 又无条件把 `$1` 当端口并 `shift`（`PORT="${1:-${MS_PORT:-}}"` 就是这种写法），于是 `--ckpt` 被吃成端口值，拼出 `--port --ckpt <路径>`。改成优先读 `MS_PORT`、`$1` 只在匹配 `^[0-9]+$` 时才当端口，对这类漏写免疫。真机踩过 |
| warmup 阶段上游持续 400 死循环 | 上游必填字段漏了。**去读上游代码确认必填项与维度，不要从默认值推**（如 DM05 `/v1/infer` 的 `observation.state` 必填，ALOHA = 14 维）。**缺字段/维度不符要显式抛错，不要补零** |
| 任务卡在「MS 节点不足」，等满 600s | 阶段 2 的 Ray 约束没真满足。进镜像 `env -i` 验裸 `ray`（`ray[default]==2.49.2` + Python `3.13.12`，且 `ray` 在**镜像 ENV 的 PATH** 上）。**平台代码对这条没有任何校验**，所以症状离根因极远 |
| `/config` 探活超时（900s） | ① 只监听了 `127.0.0.1`——BA 在另一个 Pod，必须 `0.0.0.0`；② 权重加载/warmup 放在监听之后；③ 容器内端口没真起（进 pod `curl` 一次确认） |
| 首帧 act timeout，但 `/config` 早就 200 | warmup 没在监听前做完。把权重加载 + 一次 dummy 推理都挪到 `listening` 之前 |
| 长推理中途连接被断 | `ping_interval` 没显式设 `None`，被 websockets 默认心跳误杀 |
| 每个 episode 都 `observation_failed: ValueError: 观测缺相机 'X'，实到 [...]`，而 L1 自检满分通过 | `obs.<benchmark>.json` 用了**模型内部命名**而不是 benchmark 实发的键名——自检发什么 MS 就按什么取，两边同一套假键名会自洽通过。改 `obs.<benchmark>.json` 为真实键名重跑（新版 `ms_selfcheck.py` 的 `obs_spec` 用例会拦住缺 `--obs-spec` 的情况），并在 MS 里加别名表。**不要**反过来改模型侧参数去迁就观测键名 |
| 开发机手工跑通了，上平台分数全 0 | 观测没对齐。相机**键名**、RGB/BGR、HWC/CHW、归一化、图像翻转、state 维度——以上游 reproduction 的预处理逐项对（见 `SKILL.md`「阶段 3.5」）。手工跑通用的常是作者 demo 的另一套预处理 |
| 报错消失了但分数反而更差 | 很可能是把模型侧参数（image_prompts / 相机名等训练口径）改成了观测键名。那些名字常**逐字进模型输入**（如 `label = f"{prompt} image: "`），改了不报错只错分数。正确做法是解耦：模型侧不动，另加别名表 |
| 分数低但不是 0，看不出哪错 | 动作语义。夹爪符号、delta/absolute、`unnorm_key`、chunk 截断位置、ensemble 策略 |
| 换了镜像但行为没变 | 节点有镜像缓存，**同名 tag 覆盖不生效**。每次重新保存为镜像都换一个 tag |

### 一条通用判据

**分辨率/维度不符未必报错。** 上游对错分辨率图像常常静默 resize 后正常返回 action——
这意味着它不会暴露，只会产出一个看起来正常的错分数。**L1 通过 ≠ 分数可信**；
L1 只说明服务满足协议、能真推理，分数可信要靠和上游基线比对（且样本量够）。
