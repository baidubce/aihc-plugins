# 接入表单（阶段 0 输入 ②–⑥）

用户交付的是**一个自定义 policy**，不是一套评测配置。所以 benchmark 侧的参数**一律不问用户**：
键名、shape、state 字段名、观测开关都是 benchmark 的既定事实，问了也不该采信（用户报的几乎一定是
模型侧槽位名，照它写 `obs.<benchmark>.json` 会让 L1 自检自洽通过、上平台全 0 分）。

收集按三层走，**用户只直接答 L1 的四项，再确认一次 L2**：

| 层 | 谁给 | 内容 | 怎么收 |
|---|---|---|---|
| **L1 必答** | 用户 | ② `name`、③ ckpt、④ benchmark 多选（N≥2 加权重口径）、⑥A predict 入口 | ④ 先用 `AskUserQuestion` 多选；其余由 `probe_form_defaults.sh` 预填，用户只补 `未提供` 行 |
| **L2 默认值确认** | 本 skill 查出默认值 → 用户**一次**确认 | ④ 全部观测口径、`sub_bench`、`bench_params`、⑤ harness 版本、⑥B 能从 predict 片段/模型 config 读出的项 | 回显填好的值 + `AskUserQuestion`，第一项「采用预填值（推荐）」 |
| **L3 查不出才追问** | 用户 | ⑥B 里查不出、且猜错只错分数的那几行 | 并进 G3 同一次提问（闭集做选项、开放项合成一条文本），**只问真查不出的**；不许用默认值糊过去 |

次序不可颠倒：**先定 benchmark，才有默认值可给**。四步走：

1. **选 benchmark**：`AskUserQuestion`（`multiSelect: true`），选项与描述见 SKILL.md「步 5a」；N≥2 时的 `ckpt_mode` 到 G3 再问（无默认）
2. **只读探测**：`<SSH_CMD> -o BatchMode=yes 'bash -s' < scripts/probe_form_defaults.sh`，拿到 `字段<TAB>候选值<TAB>出处`
3. **预填回显**：按下文「可探测字段与出处」把 L1 + L2 一次填好、整块回显，用户一次确认
4. **L3**：只追问回显后仍是 `未提供` 的行

**不要发空表让用户从头填**：启动脚本、ckpt、模型环境里已经有的值，让用户再抄一遍只会多一次抄错。

> ⚠️ **L2 的「默认值」只是省掉用户的输入，不降低核实标准。** ④ 的每一项仍要按
> `评测集观测口径.md` §2 查表 + harness `v0.5.0` 源码核；用户点了「采用预填值」
> **不等于**这些值被用户背书，核实仍由本 skill 负责。
> 不在 `评测集观测口径.md` 已核实清单里的 benchmark **没有可信默认值**——按 §3.9 去上游仿真器仓库
> 现查并实跑复核，查不出就停下回问，**不要填一个看起来合理的值**（步 5 原则：缺失 → 回去问）。
> ③ 的 ckpt 同理不只听填写结果，要在体检时对每条路径 `ls` 验在不在。表单只是收集，不是采信。

## L2：默认值从哪来（本 skill 自填，这张表不发用户）

L1 的 benchmark 名字定下之后，逐项查出下面这些值。**「默认值来源」一列就是唯一出处**，
不是「凭经验填」的许可；「查不出怎么办」一列是硬规定，不许改成填一个合理值。

| 字段 | 默认值来源 | 查不出怎么办 |
|---|---|---|
| ④ `images` 的 wire 键名 | `评测集观测口径.md` §2 表；参考 MS 的 `_CAMERA_MAP` **value**；benchmark 的 `make_obs` | 不在已核实清单 → 按 §3.9 去上游仓库查 + 实跑打印；**不许采用用户给的键名** |
| ④ `images` 的 H/W | 上游仿真器仓库（harness 适配层只透传 ndarray，源码里查不到） | 实跑打印 shape；**绝不抄参考 MS 的 `224×224`**（那是框架内部 letterbox 后的模型输入尺寸） |
| ④ `state_key` | §4 对照表：`state`（robodojo）\| `states`（libero 等）\| `joint_state`（robotwin） | 实跑打印 obs 顶层键名 |
| ④ `state_dim` | 实跑打印的 shape | docstring 的维度声明上游**不校验**，不得作为来源 |
| ④ `dtype_range` | 该 benchmark 的 `_to_rgb` | 实跑打印 dtype + min/max |
| ④ `sub_bench` | benchmark 有多套 suite 时取**上游默认那套**；只有一套填 `none` | 列出全部 suite 回显给用户选 |
| ④ `bench_params` | 默认 `none` | 只有「只有提交方知道」的项（任务子集、seed、渲染模式）才问用户；⚠️ 观测开关不在此处收，见下 |
| ⑤ `installed_version` | 开发机实跑 `"$MODEL_ENV/bin/python" -c "import vla_eval._version as v; print(v.version)"` | 装不上 harness → 记 `未装`，并在 `SETUP_INFO` 写明按 `v0.5.0` 核 |
| ⑥B `image_layout` / `image_order` / `image_resize_by` / `image_normalize_by` | 读 ⑥A 的 predict 片段：谁做了 resize/归一化就填 `model_internal`，否则 `ms` + 目标尺寸 | 片段里看不出 → 进 L3 追问 |
| ⑥B `image_flip` | benchmark 侧既定：libero / robocasa 已被翻过要 un-flip，其余 `none` | 按 §2 该 benchmark 条目核 |
| ⑥B `camera_slot_map` | 读 predict 片段里模型实际索引的槽位名（训练口径，**逐字进模型输入**） | 片段里看不出 → L3 追问；**不许改成 wire 键名去迁就观测** |
| ⑥B `action_dim` / `chunk_len` | 读 predict 片段的返回 shape：`(action_dim,)` → `chunk_len=1`；`(T, action_dim)` → `chunk_len=T` | 片段跑不通 → L3 追问 |
| ⑥B `state_layout` / `action_semantics` / `action_denormalize_by` | 用户训练口径，**无默认值** | 一律进 L3 追问，猜错不报错只错分数 |
| ⑥B `episode_state` | `chunk_len > 1` ⇒ 至少有动作缓存；`=1` 且片段无状态 ⇒ `none` | 片段里有历史帧队列 / rng 就逐项列出 |
| ⑥B `observation_params` | 查目标 benchmark `__init__` **自身**签名里的开关与默认值（v0.5.0 不走 MRO，不被接受的键**静默丢弃**，拼错等于没声明） | 没有可声明的开关 → 填 `none`，必须是显式结论；**不要去问用户** |
| ⑥A `deps_conflict` | 开发机实测装 `vla_eval` 是否动 torch/numpy 大版本 → 决定形态 A/B | 不敢试 → 填 `未试`，按形态 B 走 |

⚠️ **观测开关（`send_state` / `send_wrist_image`）归 ⑥B 的 `observation_params`，由 MS 在
`get_observation_params()` 里声明，绝不要写进 ④ 的 `bench_params`。** 用户填在 `bench_params` 里的
**优先级更高**（`orchestrator.py:184-189` 的 `if key not in merged_params`）⇒ 一旦同名，MS 的声明被
静默忽略、**没有任何报错**（连 `Auto-configured` 那行 info 都不会打）。所以这一项既不问用户，
也要在回显时明确告知用户别填。

⚠️ 声明成功 ≠ 取得到：robotwin 发的是 `joint_state`，声明了 `send_state` 但 MS 只读 `states`
仍然取不到（`xvla.py:211-226` 是现成反例）。`obs.<benchmark>.json` 里的 `states` 是**维度声明**，
线缆上的字段名由 `state_key` 给出，两者混淆会让自检自洽通过、上平台每帧 `observation_failed`。

### 回显与确认

查完把填好的值**整块回显**（④ 按 benchmark 分组，⑥B 随 benchmark 变的写成 `{<benchmark>: 值}`），
每行带出处注释，作为 SKILL.md **G3** 的第 1 问（选项见 SKILL.md 5c）。

**回显是给用户确认「是这个 benchmark、是这个模型口径」，不是让用户确认键名。** 用户改 ④ 的
wire 键名要一律拒绝并说明理由（两套命名空间）；要改 ⑥B 的模型侧口径则照改——那本来就是用户的事实。

## L3：只追问查不出的那几行

L2 回显后仍是空的行才进 L3，按 SKILL.md 5c 的槽位**并进 G3 同一次提问**（闭集做选项、开放项合成一条文本一行答完），
**不要把整张 ⑥B 表甩回去，也不要一行一轮**。能进 L3 的只有这几类：

- `state_layout`：顺序是约定不是推导，必须逐段写明（如 `left_arm(6)+left_ee(1)+right_arm(6)+right_ee(1)`），各段之和须等于 ④ 的 `state_dim`
- `action_semantics`：`absolute_joint_positions` \| `delta_eef` \| …
- `action_denormalize_by`：`model_internal` \| `ms`（后者要给 `unnorm_key` 或统计量）
- predict 片段跑不通时的 `action_dim` / `chunk_len` / `camera_slot_map`

这些项**不许靠猜，也不许为了消除报错反过来改它**（改模型侧参数去迁就观测键名会静默改变模型输入，
推导链见 `脚本模板.md`）。用户答不出就停在这里——宁可少算也不要算错。

## 填写示例（dm05 → RoboDojo，一份收齐后的全貌）

左侧 `[L1]` 是用户填的，`[探测]`/`[查表]` 是本 skill 查出来回显的，`[L3]` 是回显后追问到的。

```yaml
name: dm05                                  # [L1]
ckpt_mode: reuse                            # [L1]
ckpt: /mnt/pfs/models/DM05                  # [L1] 开发机真实路径，体检时 ls 验过
benchmarks:
- name: robodojo                            # [L1]
  sub_bench: none                           # [查表] 只有一套 suite
  bench_params: none                        # [查表] 观测开关不在此处，见上文 ⚠️
  images:                                   # [查表] 评测集观测口径.md §2 + 实跑打印
    cam_head:        [480, 640, 3]
    cam_left_wrist:  [480, 640, 3]
    cam_right_wrist: [480, 640, 3]
  state_key: state                          # [查表] §4：robodojo 是单数 state
  state_dim: 14                             # [查表] 实跑打印的 shape
  dtype_range: uint8 [0,255] HWC RGB        # [查表] 该 benchmark 的 _to_rgb
installed_version: 0.5.0                    # [探测] 与基线一致
model_env: /root/miniconda3/envs/dm05       # [L1]
predict_snippet: /workspace/opendm/infer.py::predict   # [L1]
runtime_downloads: none                     # [L1] 显式确认，非默认
deps_conflict: false                        # [探测] 实测装 vla_eval 不动 torch ⇒ 形态 A
image_layout: HWC                           # [探测] 片段里模型自己 resize/归一化
image_resize_by: model_internal             # [探测]
image_normalize_by: model_internal          # [探测]
image_flip: none                            # [探测] robodojo 不在 un-flip 名单
camera_slot_map:                            # [探测] 片段里模型实际索引的训练口径槽位名
  Head:        [cam_head]
  Left wrist:  [cam_left_wrist]
  Right wrist: [cam_right_wrist]
action_dim: 14                              # [探测] 片段返回 (10, 14)
chunk_len: 10                               # [探测]
episode_state: action_cache                 # [探测] chunk_len>1 必有缓存
observation_params: {send_state: true}      # [探测] robodojo __init__ 默认已 True，仍显式声明
state_layout: left_arm(6)+left_ee(1)+right_arm(6)+right_ee(1)   # [L3] 各段和=14
action_semantics: absolute_joint_positions  # [L3]
action_denormalize_by: model_internal       # [L3]
```

`camera_slot_map` 的 key 是训练口径（`Head` 逐字进模型 prompt），value 是 wire 键名——
两列不同名正是「两套命名空间」本身，**不要把 key 改成 value 去消除报错**。

## 判废规则（填完自己过一遍）

左列是收到的填法，中列是它会以什么形态失败，右列是处置。**凡是「L1 自检通过、上平台才错」的，
都不能靠跑一遍自检来发现**——只能在这张表上拦住。

| 填法 | 失败形态 | 处置 |
|---|---|---|
| ④ `images` 键名填了模型槽位名（`cam_high` / `Head` / `image_prompts` 里的名字） | L1 **自洽通过**（自检发什么 MS 就取什么），上平台每帧 `observation_failed: 观测缺相机` | 作废，按 §2 表 + 实跑重查；用户报的键名一律不采信 |
| ④ H/W 抄了参考 MS 的 `224×224` | L1 **照样全通过**（`obs_spec` 只校验格式不校验真值），上平台静默错分数 | 作废，实跑打印 shape（RoboDojo 是 `480×640`） |
| ④ `state_key` 抄成另一个 benchmark 的（robotwin 填 `states`、robodojo 填 `states`） | 每帧 `state 维度不符: None`，或 MS 取不到 state 却不报错 | 作废，按 §4 对照表定 |
| ④ `bench_params` 里出现 `send_state` / `send_wrist_image` | **静默**压过 MS 的 `get_observation_params()` 声明，连 info 都不打 | 退回用户，告知这一项由 MS 声明、不要填 |
| ③ `ckpt` 填成平台挂载后的路径 | 改造阶段 `ls` 不在；或写进 yaml 后在平台上加载错权重 | 退回，只收开发机真实路径；平台路径由 `ckptPath` 决定 |
| ③ 任一 ckpt 路径 `ls` 不在 | 自检起不来，或起来了加载的是另一份权重 | 退回用户核对，不许猜一个相近路径 |
| ⑥A `predict_snippet` 给的是 CLI 命令 / gradio / demo 脚本 | 推不出 `action_dim`、`chunk_len`、`camera_slot_map`，L3 全靠猜 | 退回，要「ckpt → model → 单帧 obs dict → action」那一段 |
| ⑥A 入口函数在多个候选里被本 skill 替用户挑了（用户没点名） | 挑到的若不是真正的 `ckpt→action` 段，`action_dim`/`chunk_len`/`camera_slot_map` 全推错且不报错 | 退回让用户点名；无法唯一确定前保持 `未提供` 进 L3，不自己挑 |
| ⑥A `runtime_downloads` 空着（不是显式 `none`） | 改造时漏建资源，上平台无外网直接炸 | 退回，必须是显式结论 |
| ⑥B `state_layout` 各段之和 ≠ ④ 的 `state_dim` | 不报错，state 按错顺序进模型，只错分数 | 退回用户逐段写明 |
| ④ 的 benchmark 不在 `评测集观测口径.md` 已核实清单里，却填了默认值 | 默认值来源不存在 ⇒ 等于凭感觉填 | 按 §3.9 现查 + 实跑复核；查不出就停下回问 |
| 任何一行留空（删行而不是写 `未提供`） | 看不出还差什么，缺项门禁失效 | 退回补 `未提供` 字面值 |

## 为什么不基于用户的启动命令包一层

⑥A 的 `launch_command` 只作线索对照初始化步骤是否漏项，**最终产物不执行它**：MS 直接在自己进程里
加载 ckpt 并推理，不去代理用户那个服务。理由四条，都不是风格问题：

- **两进程 = 两份显存管理**，打破平台「一卡一副本」（`num_gpus=1`）的前提：用户进程与 MS 各自
  按「整卡可用」分配，OOM 出现在谁身上都说不清。
- **健康探针变双层**：平台只探 MS 的 `GET /config`，900s 超时时根因可能在被代理的那一层，
  日志里看不到，定位成本成倍上升。
- **用户进程自带 batching / 异步会破坏 seq 回显与 session 隔离**：请求被重排或合并后，
  `ms_selfcheck.py` 的 `seq_echo`、`session_isolation` 两条直接 FAIL——而这是交付门禁。
- **多一跳让首帧延迟与故障归因变糊**：首帧 30s 预算里混进一次本地 HTTP 往返，超了也分不清是
  模型慢还是转发慢。

只有**闭源二进制**或**强依赖自带 serving 栈**（模型加载逻辑无法脱离该栈单独调用）时才值得付这些代价，
此时要在 `SETUP_INFO` 里写明原因，并接受 `seq_echo` / `session_isolation` 需人工论证而非机械通过。
