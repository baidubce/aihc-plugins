# 接入表单（阶段 0 输入 ②–⑥）

用户交付的是**一个自定义 policy**，不是一套评测配置。所以 benchmark 侧的参数**一律不问用户**：
键名、shape、state 字段名、观测开关都是 benchmark 的既定事实，问了也不该采信（用户报的几乎一定是
模型侧槽位名，照它写 `obs.<benchmark>.json` 会让 L1 自检自洽通过、上平台全 0 分）。

收集按三层走，**用户只直接答 L1 的四项，再确认一次 L2**：

| 层 | 谁给 | 内容 | 怎么收 |
|---|---|---|---|
| **L1 必答** | 用户 | ② `name`、③ ckpt、④ benchmark 多选（N≥2 加权重口径）、⑥A predict 入口 | ④ 先用 `AskUserQuestion` 多选；其余由 `probe_form_defaults.sh` 预填，用户只补 `未提供` 行 |
| **L2 默认值确认** | 本 skill 查出默认值 → 用户**一次**确认 | ④ 全部观测口径、`sub_bench`、`bench_params`、⑤ harness 版本、⑥B 能从 predict 片段/模型 config 读出的项 | 回显填好的值 + `AskUserQuestion`，第一项「采用预填值（推荐）」 |
| **L3 查不出才追问** | 用户 | ⑥B 里查不出、且猜错只错分数的那几行 | 并进 G3 同一次提问（闭集做选项、开放项合成一条文本），**只问真查不出的**；不许用默认值糊过去 |

次序不可颠倒：**先定 benchmark，才有默认值可给**。四步走：

1. **选 benchmark**：`AskUserQuestion`（`multiSelect: true`），选项与描述见 SKILL.md「步 5a」；N≥2 时的 `ckpt_mode` 到 G3 再问（无默认）
2. **只读探测**：`<SSH_CMD> -o BatchMode=yes 'bash -s' < scripts/probe_form_defaults.sh`，拿到 `字段<TAB>候选值<TAB>出处`
3. **预填回显**：按下文「可探测字段与出处」把 L1 + L2 一次填好、整块回显，用户一次确认
4. **L3**：只追问回显后仍是 `未提供` 的行

**不要发空表让用户从头填**：启动脚本、ckpt、模型环境里已经有的值，让用户再抄一遍只会多一次抄错。

> ⚠️ **L2 的「默认值」只是省掉用户的输入，不降低核实标准。** ④ 的每一项仍要按
> `评测集观测口径.md` §2 查表 + harness `v0.9.0` 源码核；用户点了「采用预填值」
> **不等于**这些值被用户背书，核实仍由本 skill 负责。
> 不在 `评测集观测口径.md` 已核实清单里的 benchmark **没有可信默认值**——按 §3.9 去上游仿真器仓库
> 现查并实跑复核，查不出就停下回问，**不要填一个看起来合理的值**（步 5 原则：缺失 → 回去问）。
> ③ 的 ckpt 同理不只听填写结果，要在体检时对每条路径 `ls` 验在不在。表单只是收集，不是采信。

⚠️ **观测开关（`send_state` / `send_wrist_image`）归 ⑥B 的 `observation_params`，由 MS 在
`get_observation_params()` 里声明，绝不要写进 ④ 的 `bench_params`。** 用户填在 `bench_params` 里的
**优先级更高**（`orchestrator.py:125-126` 的 `if key in merged: continue`，`_merge_observation_params` `:114-138`）⇒ 一旦同名，MS 的声明被
静默忽略、**没有任何报错**（既不打 `Auto-configured` 那行 info，也不打 warning）。所以这一项既不问用户，
也要在回显时明确告知用户别填。

⚠️ 声明成功 ≠ 取得到：robotwin 恒发 `joint_state` 14D，`send_state` 只是**另发** `states` 16D 末端位姿；
MS 要关节角却读 `states`，或要末端位姿却没声明 `send_state`，都会拿错/拿不到（对照 `xvla.py:230-234` 的读取顺序）。
`obs.<benchmark>.json` 里的 `states` 是**维度声明**，
线缆上的字段名由 `state_key` 给出，两者混淆会让自检自洽通过、上平台每帧 `observation_failed`。

### ⑥C 训练口径（回训练入口取证，**不看推理 serve 脚本**）

推理入口的默认值是「跑推理的人」定的，产出 ckpt 的默认值是训练脚本定的，两者常常不同，**而且语义可能取反**
——实测 dm05：`use_absolute_action = (data_config.action_mode == RELATIVE)`，即
「训练填 `ABSOLUTE`」在推理侧意味着「**不要**再叠一次 `state + action`」。照推理默认走就等于把绝对动作
又加了一遍当前 state：形状对、无报错、`mean_success=0`。所以这三项必须从**训练入口**取证，
每项带 `file:line`；只有训练脚本确实拿不到时才进 L3 追问。

| 字段 | 怎么取 | 不填会怎样 |
|---|---|---|
| `train_action_mode` | 训练入口的 dataclass / argparse 默认值（`ActionMode.ABSOLUTE/RELATIVE` 之类），**并追到推理管线里它如何被消费**（是否叠加 `state + action`） | 用推理默认值 ⇒ 动作整体偏移一个 state，全程跑满、0 分 |
| `train_history` | `is_history` 默认值 + 历史槽位数 + **取自哪路相机** + 采样率 + **是否含当前帧** | 不传历史 ⇒ prompt 少 N 路图，同样无报错只掉分 |
| `train_action_horizon` | 训练时的 action chunk 长度 / 训练数据里一段动作覆盖多少帧 | 训练与推理 chunk 语义不同，长程任务系统性掉分 |

回显时与 ⑥B 并列给出，形如 `train_action_mode: ABSOLUTE (playground/dm05_mem_sft_xxx.py:12)`。
**「推理默认就是训练值」不是可接受的结论**——它正是「四个没有报错但分数是错的」第 4 条。

### 回显与确认

查完把填好的值**整块回显**（④ 按 benchmark 分组，⑥B 随 benchmark 变的写成 `{<benchmark>: 值}`），
每行带出处注释，作为 SKILL.md **G3** 的第 1 问（选项见 SKILL.md 5c）。

**回显是给用户确认「是这个 benchmark、是这个模型口径」，不是让用户确认键名。** 用户改 ④ 的
wire 键名要一律拒绝并说明理由（两套命名空间）；要改 ⑥B 的模型侧口径则照改——那本来就是用户的事实。

## L3：只追问查不出的那几行

L2 回显后仍是空的行才进 L3，按 SKILL.md 5c 的槽位**并进 G3 同一次提问**（闭集做选项、开放项合成一条文本一行答完），
**不要把整张 ⑥B 表甩回去，也不要一行一轮**。能进 L3 的只有这几类：

- `state_layout`：顺序是约定不是推导，必须逐段写明（如 `left_arm(6)+left_ee(1)+right_arm(6)+right_ee(1)`），各段之和须等于 ④ 的 `state_dim`
- `action_layout`：**与 `state_layout` 同一套分段 DSL**，逐段写动作向量的顺序与每段维度，各段之和须等于 `action_dim`。段名不是只有 joint / ee 两种，按真实语义写，如
  `left_arm(6)+left_gripper(1)+right_arm(6)+right_gripper(1)`、
  `left_eef_pos(3)+left_eef_quat(4)+left_gripper(1)+...`、
  `arm_joint(7)+gripper(1)+base_vel(3)+torso(1)`（robocasa365 这类多段混合）
- `action_format`：**DimSpec `format` 串，不是段名列表**。取值只有两个来源，按优先级：
  1. **benchmark 期望值**——逐字抄 `benchmarks/<name>/benchmark.py` 的 `get_action_spec()`（robodojo = `absolute_joint_positions_with_grippers`，robotwin 关节模式 = `joint_positions` / 末端模式 = `dual_eef_pos3_quatwxyz4_gripper1`，libero = `delta_xyz` + `axis_angle` + `binary_close_positive` 三段）；多段时按 `{<段名>: <format>}` 逐段给
  2. benchmark 不在已核实清单、且 §3.9 也查不出 → 进 L3 向用户要训练口径的语义串
  **模型实际语义与 benchmark 期望不符时，不许改串迁就**（`format` 会被 harness 拿去跨端比对，改了等于把冲突藏起来）：报「口径冲突」并停，`delta` vs `absolute`、夹爪正负号这类冲突靠改 prompt/串是修不好的
- `action_params`（仅 robotwin / calvin 这类有构造参数的 benchmark）：`action_type` = `qpos`（默认，14D `joints`）\| `ee`（16D `ee_pose`）；calvin 是 `absolute_action` = `true` \| `false`。**必须与记录的 benchmark 侧 sub_bench 参数一致**：MS 声明 `ee_pose` 16D 而提交评测没传 `action_type=ee` 时，benchmark 走默认 `qpos`，16D 被**静默截断成 14** 跑完全程（`robotwin/benchmark.py:521-524`，不报错、只出错分数）。这一项要问用户、进表单、并作为 L1 自检的 `--bench-param` 一并回显
- `action_denormalize_by`：`model_internal` \| `ms`（后者要给 `unnorm_key` 或统计量）
- predict 片段跑不通时的 `action_dim` / `chunk_len` / `camera_slot_map`

> `action_format` 与 `action_layout` 分工：layout 说明**第几维是谁**（给 MS 切分用），format 说明**这段数是什么语义**（给 harness 跨端比对用）。只写 format 不够——`absolute_joint_positions_with_grippers` 里没有「哪 6 维是左臂」；只写 layout 也不够——段名相同的 `left_arm(6)` 可以是绝对角也可以是 delta。
> harness 侧比对是**按 key 交集 + `is_compatible()`**，且只打 warning 不报错：`format` 或 `dims` 任一对不上，评测照跑、分数照出，只是错的。

这些项**不许靠猜，也不许为了消除报错反过来改它**（改模型侧参数去迁就观测键名会静默改变模型输入，
推导链见 `脚本模板.md`）。用户答不出就停在这里——宁可少算也不要算错。

## 判废规则（填完自己过一遍）

左列是收到的填法，中列是它会以什么形态失败，右列是处置。**凡是「L1 自检通过、上平台才错」的，
都不能靠跑一遍自检来发现**——只能在这张表上拦住。

| 填法 | 失败形态 | 处置 |
|---|---|---|
| ④ `images` 键名填了模型槽位名（`cam_high` / `Head` / `image_prompts` 里的名字） | L1 **自洽通过**（自检发什么 MS 就取什么），上平台每帧 `observation_failed: 观测缺相机` | 作废，按 §2 表 + 实跑重查；用户报的键名一律不采信 |
| ④ H/W 抄了参考 MS 的 `224×224` | L1 **照样全通过**（`obs_spec` 只校验格式不校验真值），上平台静默错分数 | 作废，实跑打印 shape（RoboDojo 是 `480×640`） |
| ④ `state_key` 抄成另一个 benchmark 的（robotwin 填 `states`、robodojo 填 `states`） | 每帧 `state 维度不符: None`，或 MS 取不到 state 却不报错 | 作废，按 §4 对照表定 |
| ④ `bench_params` 里出现 `send_state` / `send_wrist_image` | **静默**压过 MS 的 `get_observation_params()` 声明，连 info 都不打 | 退回用户，告知这一项由 MS 声明、不要填 |
| ③ `ckpt` 填成平台挂载后的路径 | 改造阶段 `ls` 不在；或写进 yaml 后在平台上加载错权重 | 退回，只收开发机真实路径；平台路径由 `ckptPath` 决定 |
| ③ 任一 ckpt 路径 `ls` 不在 | 自检起不来，或起来了加载的是另一份权重 | 退回用户核对，不许猜一个相近路径 |
| ⑥A `predict_snippet` 给的是 CLI 命令 / gradio / demo 脚本 | 推不出 `action_dim`、`chunk_len`、`camera_slot_map`，L3 全靠猜 | 退回，要「ckpt → model → 单帧 obs dict → action」那一段 |
| ⑥A 入口函数在多个候选里被本 skill 替用户挑了（用户没点名） | 挑到的若不是真正的 `ckpt→action` 段，`action_dim`/`chunk_len`/`camera_slot_map` 全推错且不报错 | 退回让用户点名；无法唯一确定前保持 `未提供` 进 L3，不自己挑 |
| ⑥A `runtime_downloads` 空着（不是显式 `none`） | 改造时漏建资源，上平台无外网直接炸 | 退回，必须是显式结论 |
| ⑥B `state_layout` 各段之和 ≠ ④ 的 `state_dim` | 不报错，state 按错顺序进模型，只错分数 | 退回用户逐段写明 |
| ⑥C `train_action_mode` / `train_history` 照抄推理 serve 脚本的默认值（或干脆留 `未提供`） | 推理框架默认 ≠ 训练值且语义可能取反（dm05 实测：动作多叠一次 state + 缺 20 路历史），**L1 全绿、平台上跑满 max_steps 但 0 分** | 退回，回训练入口 dataclass/argparse 取证并带 `file:line`；拿不到训练脚本才进 L3 |
| ⑥B `action_layout` 各段之和 ≠ `action_dim` | 不报错，动作按错顺序下发，只错分数 | 退回用户逐段写明 |
| ⑥B `action_format` 与 benchmark `get_action_spec()` 的 `format` 不逐字一致（如少写 `_with_grippers`、把 `joint_positions` 写成 `joint_positions_with_grippers`） | harness `check_specs()` 只产 warning，评测照跑、分数是错的 | 逐字改回 benchmark 的串；若模型语义真冲突（delta vs absolute、夹爪正负），改串只是把冲突藏起来 → 停下问用户 |
| ⑥B `action_layout` 只写 joint 或 ee、漏掉混合段（`base_vel(3)+torso(1)`、`quat(4)`） | 段数凑对了但语义漏段，动作被错位消费 | 按 benchmark 声明的段名逐段写，不按「臂/末端」二选一 |
| ⑥B `action_layout` / `action_format` 按「ee=16D、joint=14D」的惯性填 | 只有 robotwin 是这两个数：libero/simpler/calvin 的末端 7D、robocasa365 13D 五段、behavior_1k 关节 23D | 一律抄 `get_action_spec()` 的值，不套记忆里的数 |
| ⑥B `action_params` 与提交评测的 sub_bench 参数不一致（MS 声明 `ee_pose` 16D，sub_bench 仍默认 `qpos`） | benchmark 把 16D **静默截断成 14** 跑完全程，不报错，整场分数作废 | 两处一起改；L1 自检必须带 `--bench-param action_type=ee` 复跑，不传只会打提示、不会 FAIL |
| ④ 的 benchmark 不在 `评测集观测口径.md` 已核实清单里，却填了默认值 | 默认值来源不存在 ⇒ 等于凭感觉填 | 按 §3.9 现查 + 实跑复核；查不出就停下回问 |
| 任何一行留空（删行而不是写 `未提供`） | 看不出还差什么，缺项门禁失效 | 退回补 `未提供` 字面值 |

## 为什么不基于用户的启动命令包一层

⑥A 的 `launch_command` 只作线索对照初始化步骤是否漏项，**最终产物不执行它**：MS 直接在自己进程里
加载 ckpt 并推理，不去代理用户那个服务。理由四条，都不是风格问题：

- **两进程 = 两份显存管理**，打破平台「一卡一副本」（`num_gpus=1`）的前提：用户进程与 MS 各自
  按「整卡可用」分配，OOM 出现在谁身上都说不清。
- **健康探针变双层**：平台只探 MS 的 `GET /config`，900s 超时时根因可能在被代理的那一层，
  日志里看不到，定位成本成倍上升。
- **用户进程自带 batching / 异步会破坏 seq 回显与 session 隔离**：请求被重排或合并后，
  `ms_selfcheck.py` 的 `seq_echo`、`session_isolation` 两条直接 FAIL——而这是交付门禁。
- **多一跳让首帧延迟与故障归因变糊**：首帧 30s 预算里混进一次本地 HTTP 往返，超了也分不清是
  模型慢还是转发慢。

只有**闭源二进制**或**强依赖自带 serving 栈**（模型加载逻辑无法脱离该栈单独调用）时才值得付这些代价，
此时要在 `SETUP_INFO` 里写明原因，并接受 `seq_echo` / `session_isolation` 需人工论证而非机械通过。

## 为什么这六项必须收齐

②–⑥ 在**步 5 前置检查之前**收齐，缺项不进第 6 步；每项都在后面被当成唯一真相源用。

| 输入 | 用在哪 | 缺了会怎样 |
|---|---|---|
| ① SSH 命令 `ssh -p <port> -i <key> <user>@<host>` | 阶段 0 全程 | 进不了开发机 |
| ② 服务短名 `<name>` | `/opt/ms-<name>/`、`SETUP_INFO`、启动命令 | 路径无法确定，中途改名要全量返工 |
| ③ ckpt 在**开发机上的真实位置**；≥2 个 benchmark 时另定 `ckpt_mode`（复用同一份 / 分别指定） | 阶段 5 自检、交付的启动命令 | 猜路径或给默认值 ⇒ 加载到错的权重也不报错。平台挂载路径**不在此处收**：由提交评测时的 `ckptPath` 决定，服务只经 `--ckpt` 取，yaml **不写** `checkpoint` |
| ④ 目标 benchmark（**可多选**）：名称 + sub_bench + 用户侧启动参数（任务子集/seed/渲染类） | 每个 benchmark 一份 `<benchmark>.yaml` + `obs.<benchmark>.json`、阶段 3.5、阶段 5 | 观测口径与观测开关**不向用户要**——采信用户给的相机键名会让自检自洽通过、上平台全 0 分。详见 `接入表单.md` |
| ⑤ harness 实际版本（`vla_eval._version.version`）与基线 `v0.9.0` 是否一致 | 阶段 3；写进 `SETUP_INFO` | 协议细节按错版本写；观测键名在版本间会变 |
| ⑥ 模型侧推理对接：conda env、最小 predict 片段、运行时资源 + 模型侧约定（图像预处理、state 打包、action 语义、chunk、per-episode 状态、要 BA（Benchmark Agent：评测时运行 benchmark 仿真环境、作为客户端连 MS 的一侧，跑在另一个 Pod）发什么）+ **⑥C 训练口径三项**：`action_mode` / `is_history`（+槽位数、取自哪路相机、采样率）/ `action_horizon`，回**训练入口**取证并带 `file:line` | 阶段 3 写 `predict`、阶段 3.5、阶段 5 人工核对 | 猜错不报错、产出看起来正常的错分数；「要 BA 发什么」漏了就收不到 state / 腕部相机；**⑥C 漏了最典型**：推理默认（`action_mode=RELATIVE`、不传历史帧）≠ 训练值 ⇒ 跑满 max_steps、0 分 |
