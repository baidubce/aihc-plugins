# 评测集观测口径速查（规定基线：tag `v0.9.0`，commit `8798464`）

写 MS 之前必须先确定三件事：**benchmark 实发的相机键名、state 的字段名与维度、指令字段名**。三者任一错位都
不会让服务崩——只会让分数错。本文按 benchmark 列出 `v0.9.0` 的实测口径与出处行号。

> ⚠️ **本表是便利品，不是权威。** 落地前仍要按 §1 的出处自己核一遍：观测键名在 harness 版本之间会变，
> 本表只对 **tag `v0.9.0`** 负责。开发机上装的若不是这一版，仍以 `v0.9.0` 为规定基线核键名，
> 并把实际版本与差异写进 `SETUP_INFO`。

## 0. 为什么没有统一 schema

`Observation` 就是 `dict[str, Any]`，没有结构约束（`src/vla_eval/types.py:14`）。同步 benchmark 的
`get_observation()` 原样返回各自 `make_obs(...)` 的结果，harness 侧不注入、不改名
（`src/vla_eval/benchmarks/base.py:290-291`），这个 dict 直接成为 `MessageType.OBSERVATION` 的 payload
（`src/vla_eval/connection.py:201`）。

⇒ **唯一权威是各 benchmark 自己的 `make_obs`。**

**图像是两层，不是一层。** 8 个 benchmark **无例外**都把相机放在顶层 `images` 这个 dict 里，
本文表格里的「images 键名」指的是**第二层**的 key：

```python
img = obs["images"]["agentview"]   # 对
img = obs["agentview"]             # 错，永远取不到
```

（`libero:274`、`calvin:632`、`simpler:340`、`robocasa:277`、`robotwin:550`、`robodojo:564`、
`behavior1k:320`、`robocasa365:239`）。而 state / 指令是**平铺在顶层**的，别跟着套一层。

`get_observation_spec()` 里的键名是契约校验用的**逻辑名**，与 wire 上的实际键名**不是同一套**，
**这是全仓库的普遍现象不是个例**——照 spec 写 MS 会错。8 个常用 benchmark **无一例外都有错位**：

| benchmark | spec 声明 | wire 实际 |
|---|---|---|
| libero | `language`（`:320`）、`state`（`:325`） | `task_description`、`states`；且 **`controller_states` 根本不在 spec 里** |
| libero_pro | 同 libero（无覆写） | 同 libero |
| calvin | `state`（`STATE_EEF_POS_EULER_GRIP` 的 DimSpec 名，`:686`） | `states` |
| simpler | **`state` 单数**（`:425`） | **`states` 复数**；且 `base_pose`/`tcp_pose` 发了但 spec 完全不声明 |
| robocasa | 只声明 1 路相机 + `state` 单数（`:306-310`） | 实发 2 路（默认 `camera_names`）+ `states` 复数 |
| robotwin | `state`（`:595`）、`ee_state`（`send_state` 时，整块 `:590-597`） | **`joint_state`**、`states` |
| robodojo | `language`（整块 `:606-610`） | `task_description`（state 侧 spec 名与 wire 都是 `state`，是唯一对齐的一项） |
| behavior_1k | 相机**摊平成顶层** `head`/`left_wrist`/`right_wrist`，另 `language` + `state`（`:397-403`） | `images` 嵌套 dict + `task_description` + `states`——**嵌套层级/单复数/spec 名三处全不一致** |
| robocasa365 | `image` 单数（`:270-271`） | `images` |

⇒ **spec 只用于跟 MS 的 `get_observation_spec()` 对账，永远不要拿它当 wire 键名去读 obs。**

## 3. 逐 benchmark 细节

行号均为 tag `v0.9.0` 下 `src/vla_eval/` 内的路径。

### 3.1 libero

`benchmarks/libero/benchmark.py:270-295`

- `agentview` ← `raw_obs["agentview_image"]`，经 `preprocess_libero_image` **只做双轴翻转** `img[::-1, ::-1]`
  + `convert_to_uint8`；该函数签名带 `resolution` **却不 resize**（`benchmarks/libero/utils.py:44-51`、`:9-13`）
  ⇒ 尺寸 = `LIBERO_ENV_RESOLUTION = 256`（定义在 `:45`，使用在 `:197-198`）⇒ **[256, 256, 3] uint8 RGB HWC**
- ⚠️ 类 docstring（`:72-74`）写着 "then resized to 256×256 with padding"，**与代码不符，是过时注释**；
  `resize_with_pad` 虽在 `utils.py:34-41` 定义，但 `preprocess_libero_image` 不调用它。只认代码。
- `wrist` ← `robot0_eye_in_hand_image`，同样**已被翻转**；模型若在非翻转数据上训练需自己 un-flip
  （X-VLA 就这么做，但**只翻 wrist 一路不含 agentview**：`model_servers/xvla.py:500-501`，
  配置开关 `unflip_wrist` 在 `:111`/`:125`，profile 读取在 `:381`）
- `states` 8D = `robot0_eef_pos`(3) + eef quat→axis-angle(3) + `robot0_gripper_qpos`(2)，
  v0.9.0 抽成了 `_proprio_state`（`:250-258`，`make_obs` 在 `:285` 调用，录像 `step` 在 `:246` 也调它），
  spec `STATE_EEF_POS_AA_GRIP`
- `controller_states` 8D（`:291-293`）**数据源不同**：取 `robot.controller.ee_pos` / `ee_ori_mat`
  → `matrix_to_quat` → `quat_to_axisangle`（`:288-290`），而 `states` 取 env obs 的 `robot0_*`。
  代码只能证明「来源不同」，**无法证明坐标系不同**，两者数值差异要自己实测。
  X-VLA 优先读它（`xvla.py:230-234` 的回退链 `controller_states` → `states` → `state`）。
  ⚠️ `controller_states` **完全不在 `get_observation_spec()` 里**（spec 只有 `agentview`/`language`/
  `wrist`/`state`，`:317-326`）⇒ 靠 spec 对账发现不了它
- ⚠️ **遗漏易错点：`quat_no_antipodal` 会改变 `states` 的数值**。构造参数 `quat_no_antipodal: bool = False`
  （`:114`），绑定在 `:119`，开启后旋转改走 `_quat_to_axisangle_robosuite`（`:32-42`，**无对极归一化**）。
  只影响 `states`，`controller_states` 固定走 `quat_to_axisangle`（`:290`）。
  键名、维度、spec 全都不变 ⇒ **这是一个连自检都发现不了的静默数值变更**，接 libero 前要跟用户确认该参数
- ⚠️ **`wrist` 与两个 state 默认都不发**：`send_wrist_image` / `send_state` 默认均为 `False`
  （`:109-110`），且两个 state 共用同一个 `send_state` 门控（`:282`）。MS 不能假定它们一定在
- suite **不改变观测键名**，只影响 `max_steps`（`MAX_STEP_MAPPING` 在 `:48-54`）：
  spatial 220 / goal 300 / object 280 / libero_10 520 / libero_90 400
- **顶层 key 全集**（无 `episode_restart` / `task_name` / `step` 之类）：`images`（`:274`，`wrist` 在 `:280`）、
  `task_description`（`:275`）、`states`（`:285`，条件）、`controller_states`（`:291`，同一条件）
- `__init__` 完整签名（`:104-115`）：`suite="libero_spatial", seed=7, num_steps_wait=10,
  send_wrist_image=False, send_state=False, absolute_action=False, max_steps=None, env_seed=None,
  quat_no_antipodal=False`

### 3.2 libero_pro

`benchmarks/libero_pro/benchmark.py` 全文 133 行，`class LIBEROProBenchmark(LIBEROBenchmark)` 在 `:40`
（import 在 `:25`），只定义 `__init__` / `_resolve_perturbation` / `_infer_base_suite` / `get_metadata`

### 3.3 calvin

`benchmarks/calvin/benchmark.py:622-651`

- `rgb_static` 由 `[-1,1]` CHW float 转成 `((x.permute(1,2,0)+1)/2*255).astype(uint8)`（`:624-625`，
  取 `raw_obs["rgb_obs"]["rgb_static"][0,0]`）⇒ **benchmark 已替你做了 CHW→HWC + 反归一化**，
  MS 再做一遍就错了。`[-1,1]` 来自 transforms 里的 `ScaleImageTensor` + `Normalize(0.5,0.5)`（`:324-325`）
- 尺寸 200×200（`Resize(size=200)` 在 `:323`，wrist 路同样的 Resize 在 `:428`；
  docstring `:174-175` 明确写 "Not configurable"）。⚠️ `size=200` 是**短边缩放**：静态相机原生就是
  200×200 ⇒ 实际 no-op；gripper 原生 84×84 ⇒ 被**放大**到 200×200（即 `rgb_gripper` 是插值上采样的结果）
- `states` 8D = `robot_obs_raw[0:7] + [14:15]`（`:643-644`），即 `[pos3, euler3, gripper_width1, gripper_action1]`
  ——**旋转是 euler 不是 axis-angle**（spec 是 `STATE_EEF_POS_EULER_GRIP`，`:686`；
  X-VLA 为此有 `euler_state=True`，`xvla.py:135`）
- ⚠️ docstring `:174` 声称观测含 scene state，**`make_obs` 从不发送**：`scene_obs` 只出现在 transforms
  配置（`:366`），`observation_space.state_obs` 只有 `["robot_obs"]`（`:304`）。与 libero 的 resize 注释
  一样是过时描述，只认代码
- 另带 `episode_restart: True`（`:647-649`），发完立刻清零。⚠️ **触发点只有「子任务切换成功」那一帧**
  （`_subtask_just_reset = True` 在 `:546`），而 `reset()` 显式置 `False`（`:489`）
  ⇒ **序列的第一帧不发这个字段**，MS 不能靠它判断「新 episode 开始」
- X-VLA 读它清缓存（`xvla.py:493-495`），但**只 pop 了 `_last_raw_actions` 与 `_last_commanded`**，
  没 pop `_current_xyz`（对比 `reset_episodes:446-448` / `finish_episodes:458-460` 三者都清）；对 calvin 无影响
  （`_current_xyz` 只有 `simpler` profile 用，`:623-631`），但别把它理解成「清掉全部闭环缓存」
- `rgb_gripper` 受 `send_wrist_image` 门控（`:636-639`），默认不发；`states` 受 `send_state` 门控，默认不发
- 5 子任务链 × 360 步 ⇒ **`max_steps` = 1800**（`EP_LEN=360` `:39`、`NUM_SUBTASKS=5` `:40`，
  `get_metadata` 在 `:662-663`）
- action 7D **无显式 assert**，由 `flatten()[:7]` 截断实现（`:590` / `:604`）——与 libero 的
  `assert len(raw_action) == 7`（`libero/benchmark.py:229`）不同，**多发的维度会被静默丢弃**
- **顶层 key 全集**：`images`（`rgb_static` 必发 `:632`，`rgb_gripper` 条件 `:639`）、
  `task_description`（`:633`，来自 `LANG_ANNOTATIONS` `:629`）、`states`（`:644`，条件）、
  `episode_restart`（`:648`，仅子任务切换帧）
- `__init__` 完整签名（`:227-236`）：`dataset_path="/data/calvin/dataset/validation",
  num_sequences=1000, seed=0, send_wrist_image=False, send_state=False, absolute_action=False, ep_len=None`

### 3.4 simpler

`benchmarks/simpler/benchmark.py:332-382`

- `primary` ← `get_image_from_maniskill2_obs_dict`（取值 `:337`），benchmark **不做任何变换**，
  spec `IMAGE_RGB`（`:421`）
- **H/W 在源码里找不到**：由上游 prepackaged config / `gym.make` kwargs 决定 ⇒ MS 不要写死尺寸
  （整个 simpler 包 + `configs/benchmarks/simpler/` 下的 **8 个 yaml**（目录里 9 个文件 = 8 yaml + README.md）
  里 grep 不到任何尺寸常量）。查法见 §3.9
- `task_name` **无条件附带**（`:342`；X-VLA widowx 按它查 per-task 夹爪阈值，`xvla.py:596-598`、`:152-157`）
- ⚠️ **state 三件套全部受 `send_state` 门控，默认 `False`**（整块 `if self.send_state:` 包住
  `:345-380`，签名 `:87-101`）。即默认配置下 simpler
  只发 `images` + `task_description` + `task_name`，一个 state 字段都没有
- ⚠️ **`states` 有两条来源、且不是稳定 8 维**：优先把 `agent["eef_pos"]` **原样透传**（`:358-360`，
  8D 只是 `:357` 的注释声明，**代码不校验**）；取不到才由 base/tcp 回退算出严格
  `pos3 + quat4_wxyz + gripper`（`:361-380`）。spec 声明的是 `RAW`（`:425`）而非 8 维 spec
  ⇒ MS 不要按固定 8 维解包
- ⚠️ spec 的键名是 **`state` 单数**（`:425`），wire 上是 **`states` 复数**（`:360`/`:380`）
- `base_pose` / `tcp_pose` **仅当两者都非 None 时才给**（`:353-355`）；两条来源都不满足时

### 3.9 H/W 在 harness 源码里查不到时怎么查

harness 的 benchmark 适配层**只透传上游仿真器渲染出来的 ndarray**，所以图像 H/W 在 harness
源码里天然查不到（robodojo §3.7、robotwin §3.6 都是这个处境）。这不是文档缺失，是分层决定的。
**正确的查法是到上游 env 仓库里查，不是"只能实跑才知道"**——四步：

## 5. 观测开关：谁来开、默认值、优先级

「obs 里到底有什么」由 benchmark 的构造参数决定（`send_state` / `send_wrist_image` 等）。
这些参数有两个来源，合并逻辑在 `orchestrator.py:114-138` 的 `_merge_observation_params`
（调用点 `:318-319`），可接受的键由 `:100-111` 的 `_accepted_init_params` 沿 MRO 收集，
构造在 `:322`（包在 `try` 里）：

下面的代码摘录自 [allenai/vla-evaluation-harness](https://github.com/allenai/vla-evaluation-harness)
tag `v0.9.0` 的 `src/vla_eval/orchestrator.py`（Apache-2.0），有删节，只加了中文注释：

```python
def _accepted_init_params(benchmark_cls):
    names = set()
    for klass in benchmark_cls.__mro__:                # ← 沿 MRO 往上收命名参数
        if klass is object or "__init__" not in klass.__dict__:
            continue
        params = list(inspect.signature(klass.__init__).parameters.values())
        names.update(p.name for p in params if p.kind in (p.POSITIONAL_OR_KEYWORD, p.KEYWORD_ONLY))
        if not any(p.kind is inspect.Parameter.VAR_KEYWORD for p in params):
            break                                      # ← 这一层不带 **kwargs 就停
    names.discard("self")
    return names

def _merge_observation_params(benchmark_cls, configured_params, observation_params):
    accepted = _accepted_init_params(benchmark_cls)
    merged = dict(configured_params)                   # ← 提交评测时填的 benchmark 参数
    for key, value in observation_params.items():
        if key in merged:
            continue                                   # ← 用户填过的优先，静默跳过
        if key in accepted:
            merged[key] = value                        # ← MS 经 HELLO 声明的
            logger.info("Auto-configured from model server: %s=%s", key, value)
        else:
            logger.warning("Model-server observation parameter %r cannot be forwarded to %s; "
                           "the benchmark constructor does not accept it", key, benchmark_cls.__qualname__)
    return merged
```

MS 侧那头的链路：`get_observation_params()` 定义在 `model_servers/base.py:314-324`
（默认 `return {}`）→ `serve.py:165` 调用 → `:166-167` 写进 `extra["observation_params"]`
→ `:177-185` `make_hello_payload(**extra)` → `:186` 回 HELLO
→ 客户端 `connection.py:95-103` 握手，把整个 payload 存成 `self.server_info`（`:103`，声明在 `:82`）
→ `orchestrator.py:318` 读它。即**这是一条单向反向通道，只在握手时生效一次**。

四条推论，每条都影响表单里这一项该问谁：

1. **MS 能自己声明**。`get_observation_spec()` 之外还有 `get_observation_params()`，返回
   `{"send_state": True}` 就能让 BA 把 state 发过来（参考 MS `robodojo_pi05.py:142-143` 即此，
   另声明了 `num_envs: 10`）。所以这不是用户信息，**不要问用户**。
2. **提交评测时填的优先级更高**（`if key in merged: continue`）。用户把同名 key 填进 benchmark 参数，
   MS 的声明被**静默忽略**——连那行 `Auto-configured` info 都不会打，没有任何报错。
3. **不被接受的键会被丢弃，但会打 warning**（`:131-136`）。可接受集合是**条件式 MRO**：
   从子类往上收集每层 `__init__` 的命名参数，遇到第一个不带 `**kwargs` 的层就停（`:100-111`）。
   名字拼错或声明了该 benchmark 没有的开关，表现是 BA 日志里一行
   `Model-server observation parameter ... cannot be forwarded to ...`，评测照跑。
   `libero_plus/benchmark.py:60-67`（`**kwargs` → `super().__init__(**kwargs)`）因此能收到父类 libero 的
   `send_state` / `send_wrist_image`；而 `libero_pro` 的 `__init__`（`:76-84`）不带 `**kwargs`，
   收集到它自己就停，libero 的其余参数对它不可见（§3.2）。
   ⚠️ v0.5.0 只核子类自身签名、不走 MRO 且**无 warning**，libero_plus 的两个开关在那时被静默丢弃；
   排查老结果时别拿 v0.9.0 的行为去推。
4. **声明成功 ≠ 取得到**。开关只决定「发不发」，发出来用什么键名、什么语义是另一回事：robotwin 恒发
   `joint_state` 14D 关节，`send_state=True` 才**另发** `states` 16D 末端位姿，两者语义不同。
   MS 只读 `states` 却没声明 `send_state`，在 robotwin 上照样取不到（`xvla.py:202` 的 robotwin profile
   同时声明了 `send_state: True` 与 `action_type: "ee"`，是正确写法，见 §4）。

默认值**逐 benchmark 不同，不要套用「默认都是关的」**：

| benchmark | 开关 | 默认 |
|---|---|---|
| robodojo | `send_state`、`num_envs` | **True**、1（`robodojo/benchmark.py:121`、`:116`；`robodojo_pi05` 声明成 10） |
| duobench | `send_state` | **True**（`duobench/benchmark.py:143`） |
| molmospaces | `send_state`、`send_wrist_image` | **True**、**True**（`molmospaces/benchmark.py:110`、`:109`） |
| libero / libero_pro | `send_state`、`send_wrist_image` | False、False（libero `:110`、`:109`；两个 state 字段共用 `send_state` 这一个 gate，`:282`。libero_pro 签名 `:76-84` 显式收这两个并透传，但**不带 `**kwargs`**，libero 其余参数对它不可见，见 §3.2 与上面推论 3） |
| libero_plus | 同 libero | 签名 `:60-67` 带 `**kwargs`，经条件式 MRO 接受父类 libero 的全部开关 |
| calvin | `send_state`、`send_wrist_image` | False、False（签名 `:227-236`，`send_wrist_image` 在 `:232`、`send_state` 在 `:233`） |
| simpler | `send_state` | False（签名 `:87-101`，`:92`）——**连带 `states`/`base_pose`/`tcp_pose` 三件套一起关**（门控 `:345-380`） |
| behavior_1k | **`send_proprio`**（不叫 `send_state`） | False（`:106`）；声明 `send_state` 会被过滤并打 warning |
| robotwin | `send_state` | False（`:247`）；`joint_state` 14D 恒发（`:559`），开了才**另发** `states` 16D 末端位姿（`:561-565`） |
| robocasa365 | **无开关** | `__init__ :127-135` 无任何观测参数，MS 声明的键全部被过滤并打 warning |
| robocasa | `send_state` | False（`:154`），开了发 `states` 9D（`:278-279`）；v0.5.0 无此开关 |

结论：开关值写进接入表单的 ⑥B.5（MS 侧约定），**查目标 benchmark `__init__` 签名得到**；
默认值已经对的也建议显式声明一次——默认值会随版本变，声明不会。

## 6. 五条必读告警

1. **state 键名有三种并存**（§4）。`obs.<benchmark>.json` 里写的 `"states": 14` 是**维度声明字段**，不是线缆字段名；
   线缆字段名由 `state_key` 给出。两者混淆会让自检自洽通过、上平台每帧 `observation_failed`。
2. **图像要取两层 `obs["images"][cam]`**（§0），且**预处理约定各不相同**：libero 双轴翻转、
   robocasa 只翻 H 轴、calvin 已做 CHW→HWC + 反归一化、其余原样转发。
   MS 里加一道「再翻一次」或「再归一化一次」不会报错，只会让分数错。
3. **「不发 state」比想象的普遍**：robocasa 的 `states` 9D 受 `send_state` 控制、默认不发（v0.5.0 无此通路）；
   **simpler 的 `states`/`base_pose`/`tcp_pose` 三件套默认全关**（`send_state=False`）；
   behavior_1k 默认也不发（且开关叫 `send_proprio`）。
   MS 声明了 `state_dim` 却等不到 state 时，必须显式失败，**不要补零**——补零会跑完全程并产出
   一份看起来正常的错分数。
4. **「可选」列不等于「一定会有」**：libero 的 `wrist` / `states` / `controller_states`、calvin 的
   `rgb_gripper`、simpler 的 state 三件套、behavior_1k 的 `states` 都要靠 benchmark 启动参数打开，
   而 robodojo / duobench / molmospaces 的 `send_state` 默认就是 `True`——**默认值逐 benchmark 不同，
   见 §5 的表，不要套用「默认都是关的」**。该发的开关由 MS 经 `get_observation_params()` 自己声明（§5），
   但**声明成功 ≠ 取得到**，MS 仍必须对缺字段做判断而不是假定。
5. **错位也会出现在 action 侧**：behavior_1k 的 `get_action_spec()`（`:394-395`）声明 `joints`，
   但 `step()` 实际只读 `action.get("actions", action.get("action"))`（`:262`）
   ⇒ **回包键名必须是 `actions`（或 `action`）**，照 spec 写 `joints` 会每帧取不到动作。
   即「spec 只用于对账、不是 wire 契约」这条对 action 同样成立。
